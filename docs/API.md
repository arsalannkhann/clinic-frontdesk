# API contract

The authoritative current schema is [openapi.json](openapi.json), generated by `clinic-voice export-openapi`. Base path `/v1/tools`; all tools require `Authorization: Bearer cvt_<credential id>.<secret>`, issued by `clinic-voice credential issue`. The server resolves clinic identity from the active credential record. Malformed, unknown, wrong-secret, expired and revoked credentials all return the same 401 with `WWW-Authenticate: Bearer`. Unknown body fields, including `clinic_id` or patient fields, are rejected.

Slot query: `doctor_id` UUID, `service_id` UUID, `day` ISO date. Valid dates are today through the clinic's `horizon_days` (default 90) ahead in clinic timezone. Inactive doctors or services return 404 for slot lookup and reservation. Slots start on a duration grid from each configured opening time, stepped in absolute time so DST changes never produce nonexistent or duplicated local times (a reservation at a nonexistent local time is rejected with 409); start + duration must fit inside the window (the buffer may run past closing). A slot must start after now and at or after now + the clinic's `lead_time_minutes` (default 60); the cutoff does not shift the grid. A candidate holds `[start, start + duration + buffer_after_minutes)` and is excluded if that overlaps an active appointment's hold `[starts_at, blocks_until)` or a schedule exception for that doctor or the whole clinic. All intervals are half-open, so a booking may start exactly at another's `blocks_until` or an exception's end. Reservations re-check the same rules under the doctor row lock. `source` in the check-slots response is `ledger_and_cached_calendar`. Cached external calendar busy time (`external_busy`, refreshed from the doctor's `busy_calendar_ids` and booking calendar) also excludes slots and blocks reservations with 409; it is advisory and only as fresh as its last refresh, and nothing schedules the worker's `calendar.refresh_busy` job yet. Time-of-day filters are not implemented.

Reservation: `doctor_id`, `service_id`, offset-aware `starts_at`. Require `Idempotency-Key` (8–128 characters, letters/digits/dot/underscore/colon/hyphen). Same key/body replays appointment; same key/different body returns 409. Offset-equivalent timestamps hash identically. Invalid/missing authentication returns 401; unknown tenant catalog objects 404; validation 422; slot conflict 409. Database errors return a generic 503 without SQL details; retry the same logical action and idempotency key after recovery.

Response includes appointment ID, `booking_reference` (8 Crockford base32 characters, unique per clinic), `pending_sync`, start/end, and cautious spoken text; the worker later confirms it (check with `appointment-status`). This contract intentionally differs from the DOCX's `book-slot` request: no caller-supplied clinic phone, free-form doctor lookup, patient name/phone, or unconditional `CONFIRMED`. The Bolna gateway (below) adapts trusted context into this API and adds patient details and verified changes (T7).

Appointment status: body `{appointment_id}`; any other field returns 422. An id that is unknown or belongs to another clinic returns 404. The response has `appointment_id`, `status`, `starts_at`, `ends_at` and `spoken_status`. Wording comes from one function (`service.spoken_status`): only a persisted `confirmed` (set by the worker after it verified the calendar event) is spoken as confirmed; `pending_sync` says it is still awaiting calendar confirmation and not yet confirmed; `needs_review` says clinic staff will follow up and it is not yet confirmed; `cancelled` says it was cancelled; anything else says it is not confirmed. A provider timeout leaves the appointment `pending_sync`, so it never yields confirmation wording. The generic tool does no caller verification; the id is an unguessable value its caller obtained from its own reservation. The Bolna gateway verifies callers (below).

Outbox review: list entries carry `id`, `kind`, `status`, `attempts`, `max_attempts`, `last_error` (a short code), `appointment_id`, `available_at`, `created_at`, `updated_at`; payloads and lease owners are not exposed. Requeue accepts only `dead` jobs and only before the appointment's start (409 otherwise). It keeps `attempts` (the worker's lease fencing relies on it only growing), sets `max_attempts = attempts + 8`, clears `last_error` and makes the job due now. For `calendar.create` whose `last_error` is a calendar failure code (so this job caused the review) it also returns the appointment from `needs_review` to `pending_sync` (same version only); the worker then re-reads the event id and re-checks external busy time first. Writes audit `outbox.requeued`. The generic `/v1/tools/appointment-status` reveals the status of any appointment id within the caller's clinic; the Bolna gateway's status tool is bound to the call session.

## Staff authentication

Staff endpoints take `Authorization: Bearer cvs_<session id>.<secret>`. Tool credentials (`cvt_`) and staff sessions (`cvs_`) are not interchangeable. The staff user's clinic is the tenant for every staff call; bodies cannot carry `clinic_id`. Login failures for unknown, disabled, locked or wrong-password accounts return the same 401. Five consecutive failures lock an account for 15 minutes. Roles: `owner` manages staff; `admin` can list staff and manage clinic configuration; `viewer` is read-only. Role and disable changes apply on the next request. Passwords are 12–256 characters; validation errors never echo them. Staff emails are globally unique, so creating an email already used by another clinic returns 409.

## Clinic configuration

`/v1/admin/*` uses staff sessions; the clinic always comes from the session and bodies carrying `clinic_id` (or any unknown field) return 422. GET is open to owner, admin and viewer; mutations need owner or admin (viewer gets 403). Any doctor, service or hours id that is unknown or belongs to another clinic returns 404 identically. PATCH bodies must contain at least one field and no nulls. `timezone` must be a canonical IANA key known to the server (e.g. `Asia/Kolkata`); `local`, empty or unknown names return 422. Hours are a list of `{weekday 0-6 (Monday=0), opens "HH:MM", closes "HH:MM"}`, at most 50 entries; `opens` must precede `closes` (the latest closing time is 23:59) and windows on one weekday may touch but not overlap. PUT replaces the whole set in one transaction (an empty list makes the doctor unbookable) and takes the same doctor row lock as reservations. Mutations write `audit_events` (`clinic.updated`, `doctor.created`, `doctor.updated`, `service.created`, `service.updated`, `hours.replaced`) with ids only. `lead_time_minutes` and `buffer_after_minutes` apply to slot lookup and reservation. A reservation snapshots its buffer into `blocks_until = ends_at + buffer_after_minutes`; later buffer edits do not change existing holds.

Schedule exceptions: `{doctor_id?: uuid, kind: holiday|leave|break, starts_at, ends_at, label?}`. Timestamps must be offset-aware; `ends_at` must be after `starts_at` and at most 366 days later, else 422. `label` (at most 80 characters, trimmed, no control characters) is an operational note such as "Diwali"; never put patient details in it. A `doctor_id` that is unknown or belongs to another clinic returns 404. Creation takes the doctor row lock (for clinic-wide: the clinic's doctor-set lock, then all clinic doctors ordered by id) before inserting, so it serializes with reservations: once it commits, no new reservation can land inside it. Active appointments whose `[starts_at, blocks_until)` overlaps the exception are returned in `conflicting_appointment_ids` (the first 100 by start time; `conflict_count` is the total) and are not cancelled; staff must resolve them. Audit actions: `exception.created`, `exception.deleted`. GET `from`/`to` are optional offset-aware query parameters; `to` must be after `from`.

Doctors also carry `calendar_account_id` (PATCH: an account of the caller's clinic, 404 otherwise, 409 if it is not active; `null` unsets it, meaning the clinic's only active account). Callback failures (unknown, expired or reused state; Google `error`; missing refresh token or scopes; rejected code) return 400 with a generic message; a non-replacing callback for a clinic that meanwhile got an active account returns 409 and stores nothing; a Google outage returns 502. Account `status` is `active`, `revoked`, or `error` (Google rejected the refresh token; reconnect with `replace=true`).

## Bolna gateway

Implemented in T6/T7 (`routes_bolna.py`, `bolna/gateway.py`, `bolna/bookings.py`); exercised only by tests, never by a live Bolna agent. All routes take the same tool credential as `/v1/tools` (`Authorization: Bearer cvt_...`); the compiled agent puts it in each tool's `api_token`, which Bolna documents as the Authorization header value. The clinic comes only from the credential. Bodies are what Bolna renders from each tool's `param` template, so every value is a string: `execution_id` (UUID, required), `from_number` and `agent_id` (Bolna call-context variables; kept only when they are E.164 / a UUID, otherwise ignored), plus the tool's own fields. Unknown fields (including `clinic_id`) return 422; validation errors never echo values. Authentication runs first (401 before any body check). A body that repeats any JSON key, at any depth, then returns 422 `{"detail": "Duplicate JSON keys are not allowed"}` before the body is parsed (defense against unescaped template substitution; see SOURCE_REVIEW.md). Responses are `Cache-Control: no-store` and never contain the caller number or patient data.

- Call session: each call upserts `call_sessions` by (clinic, `execution_id`) and commits before the tool runs. A later call may fill a missing caller number or agent id, never replace one. A session with `status=ended` (nothing sets it yet; reserved for webhooks) refuses tools with 409. Needs `TOKEN_ENCRYPTION_KEYS` and `PHONE_HASH_KEY`; without them every tool (and context with a body) returns 503 "Call session storage not configured".
- check-slots: `{doctor, service, day}`. Names are matched exactly after case and whitespace folding against active doctors and that doctor's active services (as listed by context); no fuzzy matching. Unknown names 404, duplicate names 409. Returns `{slots, spoken}`, e.g. "Open times on Wednesday 5 March: 9:00 AM, 9:15 AM or 9:30 AM." (clinic time).
- reserve-slot: `{doctor, service, starts_at}` plus optional `patient_name` (at most 120 characters, no control characters), `preferred_language` (`en`/`hi`; anything else ignored) and `consent_booking_confirmation`, `consent_reminder_call`, `consent_reminder_message` (`"true"`/`"yes"` grants; `"false"`/`"no"` declines; empty: not asked; anything else: 422 with a speakable "please answer yes or no" and nothing booked). On an existing patient matched by phone + name, grants are added but a decline or a language change applies only if this call session verified one of that patient's bookings (otherwise it is ignored; an unverified language only fills a missing one). There is no phone parameter: the patient's phone is the call session's caller number. See ADR 0006 for the patient attach policy. The response adds `booking_reference` and `spoken` ends with it spelled out ("Your booking reference is A 7 K ..."); a replay returns the same reference.
- reserve-slot key: the idempotency key is `bolna:<execution_id>:reserve-slot:<first 24 hex of sha256(canonical JSON of resolved doctor_id, service_id and UTC starts_at)>`; it goes through the same advisory-locked replay as `/v1/tools/reserve-slot`, so a Bolna retry with identical arguments (any offset representation) replays the same appointment and different arguments make a different key. The same arguments in another execution are a new action (normally 409, slot taken). The appointment records `call_session_id`. One call session may hold at most 3 (`gateway.MAX_SESSION_ACTIVE`) of its own reservations, counting those still `pending_sync`/`confirmed` and those moved by a reschedule (appointments created by a reschedule do not count); a further new reservation returns 409 with a speakable handoff message (replays are not capped; the check runs under a session row lock inside the reservation transaction). `/v1/tools/reserve-slot` rejects `Idempotency-Key` values starting `bolna:` (422). Returns `{appointment_id, booking_reference, status, starts_at, spoken}`; `spoken` comes from `service.spoken_status` of the appointment's current status, so a replay of an appointment since cancelled or sent for review says so.
- appointment-status: `{appointment_id}`. Only appointments whose `call_session_id` is the session of the same clinic and `execution_id`, or that this session verified; anything else (another execution, another clinic, an appointment made through `/v1/tools`) is 404. Returns `{appointment_id, status, spoken}` with `spoken` from `service.spoken_status`: only persisted `confirmed` says confirmed.
- context: no body for a plain fetch; when called as a tool, the call-context body also records the session. FAQ and emergency texts are fixed placeholders until clinic-approved text exists.

- verify-booking: `{booking_reference}` (as spoken; case, spaces and hyphens ignored, O read as 0, I/L as 1). 200 `{booking_reference, status, starts_at, doctor, service, spoken}` only when that reference names an appointment of the clinic whose patient phone hash equals the session's caller-number hash. Wrong, malformed, another phone's or another clinic's reference, and a session without a caller number all return the identical 404 `bookings.VERIFY_FAILED`. Each distinct failed attempt counts once per session (a retry of the same attempt does not); the third returns 403 `bookings.HANDOFF`, and from then on verify, cancel and reschedule return that 403 for this session. A success is recorded for this session and appointment only; replays return the same result. Bookings are never listed or searched by phone.
- cancel-booking: `{booking_reference, confirmed}`. 403 `NOT_VERIFIED` unless this session verified that reference. `confirmed` other than `true`/`"true"` returns 200 `{changed: false, ...}` with a read-back prompt and changes nothing. With `confirmed: true`: status `cancelled`, `version` + 1, `calendar.cancel` for the old version's event, all in one transaction; 200 `{changed: true, status: "cancelled", spoken}`. 409 when the booking is no longer active or has started. Replays (key `bolna:<execution>:cancel-booking:<digest>`) return the same result.
- reschedule-booking: `{booking_reference, starts_at, confirmed}`. Same verification and read-back rules. The new start must be an open slot for the same doctor and service (the old hold is released inside the same transaction, so overlapping it is allowed). Success creates a new appointment (new id, version 1, new `booking_reference`, `rescheduled_from` = old id, same patient, verified in this session), cancels the old one (`version` + 1) and enqueues `calendar.cancel` (old) and `calendar.create` (new). 200 `{changed: true, booking_reference (new), previous_booking_reference, status: "pending_sync", starts_at, spoken}`; the spoken text says the appointment was moved and is not yet confirmed. Slot taken, outside hours or an exclusion violation: 409 `UNAVAILABLE` with the original intact; beyond the horizon: 422. Concurrent changes of one booking yield exactly one outcome (the other gets 409). Replays (key over appointment id and UTC start) return the same new booking.

## Staff appointments

`GET /v1/admin/appointments` returns `{id, booking_reference, doctor_id, service_id, starts_at, ends_at, status, rescheduled_from, created_at, patient_name, phone_last2}`. `patient_name` and `phone_last2` are filled only for owner/admin (and only when `TOKEN_ENCRYPTION_KEYS` decrypts them); viewers always get null; full phone numbers are never returned. Each appointment listed with decrypted patient data writes one `appointment.patient_details_viewed` audit row targeting it. `booking_reference` is returned to every role. `status` filters by one of `pending_sync`, `confirmed`, `needs_review`, `cancelled`. Cancel accepts an active appointment (409 otherwise), bumps its version, enqueues `calendar.cancel` and writes `appointment.cancelled`. Resolve accepts only `needs_review` (409 otherwise): `cancel` cancels like the cancel route (`appointment.resolved_cancel`); `requeue` requeues the dead `calendar.create` job of the current version through the outbox requeue (writes `outbox.requeued` and `appointment.resolved_requeue`) and returns the appointment to `pending_sync`, and is refused with 409 when no such job failed with a calendar code or the appointment has started. Unknown or foreign ids return 404.

## Bolna execution webhooks

Implemented in T8 (`routes_webhooks.py`, `bolna/webhooks.py`, `handlers/bolna.py`); exercised only by tests with synthetic payloads, never by a live Bolna delivery. Bolna posts the execution payload (the `GET /executions/{id}` shape) to the agent's `webhook_url` on each status change.

- Authentication: `POST /v1/webhooks/bolna/cvw_<credential id>.<secret>`, a `tenant_credentials` row with scope `webhook` (`clinic-voice credential issue --scope webhook`). Bolna documents no signature and no API field for webhook headers, so the credential is a path segment (ADR 0007). Malformed, unknown, wrong-secret, revoked, expired and tool (`cvt_`) credentials all return 401 `{"detail": "Invalid credentials"}`. A `webhook` credential does not authenticate the tool APIs. The clinic comes only from the credential.
- Checks, in order, each refusing with nothing stored: source address against `BOLNA_WEBHOOK_ALLOWED_IPS` when set (403); credential (401); body larger than `WEBHOOK_MAX_BODY_BYTES` (default 65536) by Content-Length or while streaming (413); a body that is not a JSON object with a UUID `id` and a status matching `^[a-z][a-z-]{0,31}$`, or has duplicate keys (422 `{"detail": "Unrecognized webhook event"}`, nothing echoed); when the clinic has a configured Bolna agent id, a payload whose `agent_id` differs or is missing (403). Multiple X-Forwarded-For header lines are joined before the hops-th address from the right is taken, and IPv4-mapped IPv6 addresses compare as IPv4.
- Stored fields (allowlist): execution id, status, agent id, created/initiated/updated timestamps (offset-aware only), conversation and telephony durations, termination reason, hangup reason and hangup_by (codes matching `^[A-Za-z][A-Za-z_-]{0,63}$`: letters, underscore, hyphen; no digits or dots), numeric hangup provider code, call type (`inbound`/`outbound`), numeric total cost. Transcript, summary, extracted data, recording URL, phone numbers, context details, error message, smart status and every other field are dropped.
- Response: 200 `{"status": "accepted"}` after the inbox row and its `webhook.process` job committed, or `{"status": "duplicate"}` when the same event (execution id + status + SHA-256 of the minimized payload) was already stored for this clinic. `Cache-Control: no-store`.
- Processing (worker): the event updates the call session with the same clinic and execution id. Status is monotonic (scheduled/rescheduled < queued < initiated < ringing < in-progress < call-disconnected < final, where final is completed, balance-low, busy, no-answer, canceled, failed, stopped or error). A lower status, any status after a different final one, or an equal-rank event whose `updated_at` is older than (or, once one was recorded, missing compared with) the latest applied one is recorded as `ignored`/`stale`. With a configured agent id, an event without or with another agent id is `agent_mismatch`. `call-disconnected` and final statuses end the session (tools then return 409). Events for an execution without a session are kept as `ignored`/`unknown_execution`; no session is created.

Credential administration over HTTP, provisioning, and provider administration endpoints are backlog items. No live Bolna tool payload is shipped as provider-validated JSON: `clinic-voice bolna compile-agent` prints a compiled agent built from the documentation (docs/SOURCE_REVIEW.md), unverified against the live API.

## Confirmations, reminders and opt-out

Implemented in T9 (migration 014, `reminders.py`, `handlers/reminders.py`, ADR 0008); exercised only by tests against FakeMessaging and FakeBolna. Nothing contacts a patient unless the clinic's `outbound_enabled` is true (default false), the patient has an active consent for the purpose, and no opt-out matches.

- Clinic settings: `outbound_enabled` (bool), `quiet_hours_start`/`quiet_hours_end` (clinic-local `HH:MM`, default 21:00/09:00; a start after the end wraps midnight; equal values are 422, including a one-sided change that would make them equal), `reminder_lead_minutes` (default 1440), `daily_contact_budget` (default 200 per clinic-local day; 0 sends nothing). Changes of `outbound_enabled` are audited as `clinic.outbound_enabled`/`clinic.outbound_disabled`.
- Contacts: a confirmation message is planned when the worker confirms an appointment (consent `booking_confirmation`), and a reminder call/message at `starts_at - reminder_lead_minutes` (consents `reminder_call`/`reminder_message`), each shifted out of quiet hours and within the budget, never later than 30 minutes before the appointment. Message text is fixed: clinic name, appointment date/time and booking reference only; it is composed at send time and never stored. Reminder calls go through Bolna `POST /call` with the clinic's `bolna_agent_id` and `user_data` {`call_purpose`, `clinic_name`, `appointment_time`, `booking_reference`, `contact_reference`}.
- Reminder statuses (`GET /v1/admin/reminders`): `scheduled`, `sending`, `sent`, `unknown` (ambiguous timeout, being reconciled), `needs_review` (outcome unknown and no lookup exists: staff check the provider dashboard by `provider_execution_id` or contact reference), `cancelled` (`appointment_changed`, `stale`), `suppressed` (`no_consent`, `opted_out`, `quiet_hours`, `budget_exhausted`, `outbound_disabled`, `too_late`, `expired`, `no_phone`, `no_patient`), `failed` (`provider_permanent`, `agent_unconfigured`, `keyring_unconfigured`, `job_dead`). `stop_outcome` (`stopped`, `not_stoppable`) records a cancellation's stop of a placed call.
- opt-out tool: `{booking_reference, scope}` with the usual call context. `scope` is `all` (also empty), `calls` or `messages`. It requires that this session verified the reference with verify-booking (reference + caller number). Otherwise it returns 403 with a speakable sentence (verify first, or clinic staff can help) and records nothing. The handoff state returns the handoff 403. 409 if the booking has no patient record. 200 `{opted_out: true, scope, spoken}`; repeating it is harmless. It never applies to the caller's number alone.
- reserve-slot: when an unverified caller declines a purpose that the matched patient has already granted, the decline is not applied (ADR 0006) and `spoken` adds that changing an existing preference needs verification on this call or clinic staff.
