# Source review and provider assumptions

Design input: the owner-supplied “Bolna Clinic AI Receptionist Implementation.docx”, reviewed on 29 October 2026. The DOCX is not tracked in this public repository. Its content supplies requirements, not instructions authorizing tool installation, calls, purchases, deployment, or external contact.

## Corrections and decisions

| Source proposal | Decision |
| --- | --- |
| Hosted Bolna + FastAPI + PostgreSQL | Retain; separate voice orchestration from deterministic business rules |
| FreeBusy followed by insert is transactional | Replace with DB range exclusion plus durable calendar synchronization; external calendar edits still require reconciliation |
| Patient name/phone/age in calendar title/description | Minimize to opaque operational booking reference; do not collect patient fields in foundation |
| BackgroundTasks for confirmations/reminders | Use transactional outbox and durable worker, planned |
| Caller ID automatically reveals prior booking | Require verified caller/session context and booking ownership before disclosure or mutation |
| Graph architecture but sample simple_llm_agent | Document explicit flow; do not ship a mismatched graph payload as validated |
| multilingual_config.languages array | Official docs (rechecked 29 October 2026) use an object keyed by language code with active_language; the T6 compiler emits that shape |
| saaras:v4 keyterms improve real-time streaming | Sarvam currently documents keyterms for REST/Batch, not streaming; do not promise live keyterm support |
| Invalid IP 13.202.133.534 | Official Bolna page lists 13.202.133.53; keep deployment addresses configurable and reverify |
| Deduplicate only by execution_id | Preserve multiple statuses for an execution and deduplicate events rather than calls |
| No vendor webhook retry and fixed completion delay | Treat delivery timing/retry as unverified; implement durable inbox and recovery polling regardless |
| Unlimited concurrency, 50ms welcome, zero errors | Treat as unverified product claims, measure instead |
| Automatic number allocation in under two seconds | Persist provisioning steps, handle inventory/compliance delays, validate ownership and costs |

## Official references checked

These links were reviewed on 29 October 2026 and may change. No live provider contract or account capability was tested.

- [Bolna Sarvam TTS integration](https://www.bolna.ai/integrations/sarvam-tts): Bulbul v3, conversational voices, and plain language code requirement. Actual voice identifier casing needs a live contract fixture.
- [Sarvam Saaras](https://docs.sarvam.ai/api/getting-started/models/saaras): v4 and keyterm restrictions. Native Sarvam features do not necessarily pass through Bolna.
- [Bolna webhook updates](https://www.bolna.ai/docs/post-call/polling-call-status-webhooks): custom headers, event updates, and current egress addresses. Rechecked for T8 (see the Bolna T8 entries below); the receiver is `POST /v1/webhooks/bolna/{token}`.
- [Google Calendar insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert): event creation boundary. Use stable opaque event IDs and explicit recovery semantics in the adapter.
- Google OAuth and Calendar (T5), reviewed on 29 October 2026; only `httpx.MockTransport` fixtures were exercised, never a live Google endpoint:
  - [OAuth 2.0 for web server applications](https://developers.google.com/identity/protocols/oauth2/web-server): authorization endpoint `https://accounts.google.com/o/oauth2/v2/auth`, `access_type=offline`, `prompt=consent`, `include_granted_scopes`, `state`, `error` on the redirect; token endpoint `https://oauth2.googleapis.com/token` (authorization_code and refresh_token grants; `scope` lists granted scopes; `refresh_token` only with offline access); revoke endpoint `https://oauth2.googleapis.com/revoke` (POST, form `token`; 200 on success, 400 with an error code otherwise). Its "Token revocation" section (re-read 29 October 2026) says revocation "removes all OAuth 2.0 scopes previously granted to a project, invalidating any issued access or refresh tokens for all clients registered under that project" and that revoking an access token also revokes its refresh token; effect may be delayed. The code therefore treats revocation as grant-wide for the Google user: superseded (`replace=true`) and rejected grants are not revoked, only an explicit disconnect is; redirect URIs must be https except loopback. Uncertainty: this page does not document PKCE for web clients.
  - [OAuth 2.0 for iOS and desktop apps](https://developers.google.com/identity/protocols/oauth2/native-app): PKCE parameters (`code_verifier` 43-128 characters, `code_challenge` = base64url SHA-256 without padding, `code_challenge_method` S256). PKCE with a confidential web client is applied here on the basis of RFC 7636 and Google's PKCE support; confirm with a live test client that the token endpoint accepts `code_verifier` together with `client_secret`.
  - [Calendar API scopes](https://developers.google.com/workspace/calendar/api/auth): chosen `calendar.events` (events insert/get/delete) and `calendar.freebusy` (availability). Narrower `calendar.events.owned` was not chosen because a booking calendar shared to (not owned by) the connecting account would fail; `calendar.app.created` would require the system to create the calendar. Revisit when the onboarding flow decides calendar ownership. Both scopes are classed sensitive by Google, so a public OAuth client needs verification.
  - [events.insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [events.get](https://developers.google.com/workspace/calendar/api/v3/reference/events/get), [events.delete](https://developers.google.com/workspace/calendar/api/v3/reference/events/delete), [Events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events): client ids in base32hex, 5-1024 characters; `dateTime` RFC 3339 with offset; `transparency` opaque; `extendedProperties.private`; deleted events have status `cancelled` and get "always returns them", but only the id is guaranteed and they eventually disappear (adapter: placeholder times for cancelled events without times; 404 thereafter maps to None). The insert page does not document the duplicate-id status; 409 comes from the errors guide.
  - [Calendar API errors](https://developers.google.com/workspace/calendar/api/guides/errors): 401 refresh; 403 `rateLimitExceeded`/`userRateLimitExceeded` and 429 backoff; 404 not found; 409 duplicate id; 410 deleted (deleting an already deleted event); 500 backoff. 403 `quotaExceeded` has no retry guidance and is treated as permanent. 404 can also mean an inaccessible calendar; the adapter's get then returns None and the following insert fails permanently.
  - Reachability check before treating a DELETE 404 as success: an `events.list` call with `maxResults=1` on the same calendar (covered by `calendar.events`). Revoke treats HTTP 400 with `error=invalid_token` as already revoked; this response shape is the standard OAuth one but was not confirmed on Google's pages and needs a live check.
  - [freebusy.query](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query): `calendars.(id).errors[]` with reasons `groupTooBig`, `tooManyCalendarsRequested`, `notFound`, `internalError` (more may be added); scopes include `calendar.freebusy`.
- Bolna (T6), fetched 29 October 2026 with WebFetch/curl (markdown pages, `.md` suffix). Nothing was sent to the Bolna API; every shape below is "unverified against live API" until an owner-authorized test agent confirms it. Pages:
  - [Agent v2 create](https://www.bolna.ai/docs/api-reference/agent/v2/create.md): `POST https://api.bolna.ai/v2/agent`, Bearer API key; body `{agent_config: {agent_name, agent_welcome_message, webhook_url, tasks: [{task_type, toolchain {execution, pipelines}, tools_config {llm_agent, synthesizer, transcriber, input, output, api_tools, multilingual_config}, task_config}]}, agent_prompts: {task_1: {system_prompt}}}`; 201 `{agent_id, state, version_id}`. GPT-5 models need `temperature: 1`. Telephony `input`/`output` provider enum includes plivo, twilio, exotel, vobiz; format `wav` for those.
  - [Agent v2 update](https://www.bolna.ai/docs/api-reference/agent/v2/update.md): `PUT /v2/agent/{agent_id}` with the full body; 200 `{agent_id, status: "updated"}`. The multilingual page says PATCH cannot change `tools_config`, so the compiler output is always sent whole.
  - [Custom functions](https://www.bolna.ai/docs/tool-calling/custom-function-calls), [schema](https://www.bolna.ai/docs/tool-calling/custom-function-schema.md), [examples](https://www.bolna.ai/docs/tool-calling/custom-function-examples.md): a tool has `name`, `description`, optional `pre_call_message`, `parameters` (JSON schema; types string/integer/number/boolean), `key: "custom_task"` and `value {method, url, param, api_token, headers}`; `param` maps names to `%(name)s` specifiers whose names must equal the property names; `api_token` is the Authorization header value (`Bearer ...`); `headers` holds extra headers. Bolna source IPs listed: 13.203.39.153, 13.126.9.249, 13.202.133.53. **Ambiguity:** the API reference types `api_tools` as `tools` (an array, described as "a JSON string") plus `tools_params` keyed by tool name with `{method, url, api_token, param}` where `param` is stringified JSON; its schema only models `transfer_call`, and it lists no `headers` there. The compiler emits the API shape (`tools` array of schemas with `key: custom_task`, `tools_params[name] = {method: POST, url, api_token, param: <JSON string>}`), puts the tenant credential in `api_token` and sends no custom `headers` field. Unverified against live API: custom_task through the API, array vs string `tools`, POST body equals the rendered `param`. **Escaping of `%(name)s` substitution is unverified:** the docs do not say whether substituted values are JSON-escaped inside the `param` string. If they are not, an LLM-collected value containing a quote could inject keys. Mitigations: the compiler puts the platform-rendered context fields (`execution_id`, `from_number`, `agent_id`) last in every template, and every `/v1/bolna/*` route rejects a body with any duplicate JSON key (422, fixed message). An injected value can still break the JSON or the field types, which fails validation (422) rather than being misread.
  - [Call-context variables](https://www.bolna.ai/docs/tool-calling/custom-function-variables.md) and [using context](https://www.bolna.ai/docs/prompting/using-context.md): system variables `agent_id`, `execution_id`, `call_sid`, `from_number` (number that initiated the call), `to_number` (number that received it), `current_date`, `current_time`, `timezone`; `{var}` or `{{var}}` in prompts; variables defined in the prompt are "auto-substituted" into custom function params instead of being collected by the LLM. **Ambiguity:** the variables page lists only agent_id, call_sid, from_number and to_number, and the docs do not say whether the platform or the LLM writes the value into the call. The gateway therefore treats `execution_id`, `from_number` and `agent_id` as provider-asserted (never identity; see SECURITY.md). For inbound calls `from_number` is the caller. **How the first live test call answers this:** every `/v1/bolna/*` route refuses a body whose `execution_id`, `from_number` or `agent_id` still looks like a template (braces, a `%(name)s`-style specifier, a variable name in angle brackets such as `<from_number>`, or a bare variable name) with 422 `context_unsubstituted` and logs `call context unsubstituted clinic=<id> tool=<tool> fields=<names>`; an absent, `null` or blank `execution_id` gets 422 `context_missing` and `call context missing ...`. An accepted request whose `from_number` or `agent_id` is empty or malformed (not E.164, such as `None`, `null` or `unknown`; not a UUID) is not refused, but logs `call context incomplete clinic=<id> tool=<tool> empty=<names> malformed=<names>`. If the first test call's tools succeed, the call session has a caller hash and no `incomplete` line appears, Bolna (or the prompt variables) filled the values; a `context_unsubstituted` or `context_missing` refusal shows they arrived unrendered or empty, and an `incomplete` line shows a rendered but unusable value, naming which ones. It cannot detect an LLM inventing a well-formed value, so compare the stored session's execution id with the webhook/execution record for the same call before relying on caller-number verification.
  - [Multilingual quickstart](https://www.bolna.ai/docs/quickstarts/multilingual) and [config reference](https://www.bolna.ai/docs/customizations/multilingual-config-reference.md): `tools_config.multilingual_config {enabled: true, active_language, language_switch_trigger ("requested_or_auto_detected" | "caller_requested"), languages: {<code>: {transcriber, synthesizer, system_prompt, handoff_message, agent_name}}}`, at least two languages; the base transcriber/synthesizer are overridden per language (the docs' example overrides only `transcriber.language`).
  - [Sarvam voice](https://www.bolna.ai/docs/sarvam-voice.md): synthesizer `provider: sarvam`, `provider_config {voice, voice_id, model (bulbul:v3 | bulbul:v4-flash; v2 no longer selectable), language (plain code such as hi), speed 0.5-2.0}`; voices do not carry across model generations (400). [Sarvam transcriber](https://www.bolna.ai/docs/sarvam-transcriber.md): `model saaras:v4` (recommended; only one accepting `keywords`) or `saaras:v3`, `language` plain code (`en`, `hi`, ...), `stream`, `endpointing`. Default voice `Suhani`/`suhani` on bulbul:v3 is the docs' example, not a listening-tested choice.
  - [Get execution](https://www.bolna.ai/docs/api-reference/executions/get_execution.md): `GET /executions/{execution_id}`; status enum scheduled, queued, rescheduled, initiated, ringing, in-progress, call-disconnected, completed, balance-low, busy, no-answer, canceled, failed, stopped, error; `telephony_data.call_type` inbound/outbound. The adapter keeps only id, agent_id, status, termination_reason, call_type and conversation_duration (no transcript, numbers, recording or extracted data). Which statuses are terminal is our reading, not documented as such. Bolna does not document whether a 5xx on a write means nothing happened, so the adapter treats write 5xx (and 429, except on `POST /call` where it is documented as nothing queued) as an unknown outcome.
  - [Webhooks](https://www.bolna.ai/docs/post-call/polling-call-status-webhooks): agent `webhook_url`; payload matches the execution API; an "Add headers" toggle exists in the dashboard but the field format is not documented; retries not described. Superseded by the T8 recheck below; since migration 017 the compiler sets `webhook_url` (provisioning passes a managed webhook-scope credential as its last path segment; `compile-agent` prints it redacted).
  - Agent reads (T10, fetched 29 October 2026; nothing sent to the API): [Get agent](https://www.bolna.ai/docs/api-reference/agent/v2/get.md) `GET /v2/agent/{agent_id}` → AgentV2 `{id, agent_name, agent_type, agent_status (seeding|processed), created_at, updated_at, tasks[{task_type, tools_config {..., api_tools}, toolchain, task_config}], ingest_source_config, call_summary_enabled, agent_prompts}`; only 200 and 400 are documented (no 404; the adapter treats a 404 as unknown). [Get all agents](https://www.bolna.ai/docs/api-reference/agent/v2/get_all.md) `GET /v2/agent/all` → array of AgentV2, no query parameters, no pagination documented. Not documented: `webhook_url` in the response, whether `api_token` is returned or masked, read-after-write consistency of the listing, and uniqueness of `agent_name`. The adapter keeps id, name, tool URLs and the credential id parsed from each `api_token`; `BolnaClient.consistent_agent_lookup` is False, so an ambiguous create that the listing does not show goes to manual review. A large account whose listing exceeds the 1 MiB response cap reads as retryable and ends in manual review.
  - [Phone numbers list](https://www.bolna.ai/docs/api-reference/phone-numbers/get_all.md): `GET /phone-numbers/all` → array of `{id, phone_number, agent_id, telephony_provider, rented, ...}`. [Set inbound agent](https://www.bolna.ai/docs/api-reference/inbound/agent.md): `POST /inbound/setup {agent_id, phone_number_id}`. Purchase (`/phone-numbers/buy`) is deliberately not implemented.
  - [Make call](https://www.bolna.ai/docs/api-reference/calls/make.md): `POST /call {agent_id, recipient_phone_number, from_phone_number?, scheduled_at?, user_data?}` → `{message, status: queued, execution_id}`; 429 `{retry_after_seconds}` when a new number is still activating. [Stop call](https://www.bolna.ai/docs/api-reference/calls/stop_call.md): `POST /call/{execution_id}/stop` for queued or scheduled calls. T9 uses both (not rechecked live): reminder calls are placed at their due time without `scheduled_at` and carry `user_data`; the reference review lists no idempotency key for `POST /call` and no execution lookup by client reference, so a timed-out call cannot be reconciled and goes to staff review. No opt-out field or disposition value is documented in the execution payload, so webhook opt-out is not implemented. No messaging provider has been reviewed or chosen. A messaging provider's review must establish, from official documentation, whether sends are deduplicated by a client reference (`idempotent_reference`) and whether lookup by that reference is read-after-write consistent (`consistent_lookup`); providers/messaging.py resends after a not-found lookup only when both hold. Reminder calls use a separate outbound agent id (`agent_id` of `POST /call`); the docs reviewed say nothing about restricting an agent's tools per call, so the outbound agent must be configured without tools.
  - Not fetched: `https://www.bolna.ai/docs/api-reference/openapi.yml` (404); pre-call webhooks page (not used).
- Bolna webhooks (T8), rechecked 29 October 2026 with WebFetch (markdown pages). No delivery from Bolna has been received and nothing was sent to Bolna; every point is "documented, unverified against live behaviour" unless marked otherwise:
  - [Webhook updates](https://www.bolna.ai/docs/post-call/polling-call-status-webhooks.md): Bolna sends an HTTP POST with the current execution data to the agent's webhook URL; the payload has "the same structure" as the Get Execution response and Call History raw data. Example progression scheduled → queued → in-progress → completed. **Signing: not mentioned** (no signature header, no shared secret). Custom headers: a dashboard "Add headers" toggle "to attach custom headers", with no documented names, format or API field. **Event id: not mentioned.** **Retries: not mentioned.** Source IPs: 13.203.39.153, 13.126.9.249, 13.202.133.53 ("whitelist all three").
  - [Agent v2 create](https://www.bolna.ai/docs/api-reference/agent/v2/create.md) (rechecked): `agent_config.webhook_url` ("Webhook URL to receive data for all conversations") is the only webhook field; there is no header, secret or signature field in the API schema. The same three source IPs are listed. Decision: the per-clinic webhook credential is a URL path segment (ADR 0007).
  - [Webhook delivery health](https://www.bolna.ai/docs/post-call/webhook-delivery-health.md): a delivery counts as delivered on any 2xx; any other status, a timeout (duration not given) or a connection failure counts as failed. Bolna posts once per status change. Retries, redelivery, delivery guarantees and duplicates are **not described**. Failed deliveries are downloadable as CSV with header values excluded. Decision: persist before 2xx, dedupe anyway, reconcile by polling.
  - [Call statuses](https://www.bolna.ai/docs/post-call/list-phone-call-status.md): scheduled, queued, rescheduled, initiated, ringing, in-progress, call-disconnected ("ended, post-call processing pending"), completed, balance-low, busy, no-answer, canceled (one l), failed, stopped, error. Only `completed` is called "the final status of every conversation". Treating balance-low, busy, no-answer, canceled, failed, stopped and error as final too, and the rank order used for monotonic updates (`providers.bolna.STATUS_RANK`), is **our reading**, not documented.
  - [Execution payload](https://www.bolna.ai/docs/post-call/execution-payload.md): top-level `id` (uuid, the execution id; "repeated webhook deliveries for one call share it", and the page says to deduplicate on it), `agent_id`, `batch_id`, `campaign_id`, `status`, `termination_reason`, `smart_status`, `error_message`, `conversation_duration` (seconds), `answered_by_voice_mail`, `created_at`, `initiated_at`, `updated_at`, `scheduled_at`, `rescheduled_at`, `user_number`, `agent_number`, `provider`, `transcript`, `summary`, `extracted_data`, `telephony_data {duration, to_number, from_number, recording_url, hosted_telephony, provider_call_id, call_type, provider, hangup_by, hangup_reason, hangup_provider_code}`, `total_cost` (cents), `cost_breakdown`, `usage_breakdown`, `latency_data`, `tool_call_logs`, `transfer_call_data`, `context_details`, `agent_context_details`, retry fields. **No separate event id.** Deduplicating on `id` alone would drop later statuses of the same call, so the event key is execution id + status + SHA-256 of the minimized payload. Timestamp format is not specified; only offset-aware ISO 8601 values are kept. Whether `termination_reason`/`hangup_reason`/`hangup_by` are fixed codes is not documented. The stored pattern `^[A-Za-z][A-Za-z_-]{0,63}$` (letters, underscore, hyphen; no digits, dots or spaces, so no phone numbers or free text) is **unverified**: real Bolna values that contain digits or other characters are dropped until a live payload shows the actual vocabulary. Stored allowlist: id, status, agent_id, created/initiated/updated_at, conversation_duration, telephony duration, termination_reason, hangup_reason, hangup_by, hangup_provider_code, call_type, total_cost. Never stored: transcript, summary, extracted_data, recording_url, numbers, context details, error_message, smart_status.
- [PostgreSQL ranges](https://www.postgresql.org/docs/current/rangetypes.html): half-open time ranges and exclusion constraints.
