# Security and privacy design

## Current controls

Secret configuration is required at startup and redacted in settings representation. Tool bearer tokens are per-clinic credential records (`tenant_credentials`): 256-bit random secrets, stored only as SHA-256 digests, shown once at issue, with expiry, overlap-window rotation, immediate revocation and coarse last-used tracking. Credential administration is CLI-only (operator access to the database); there is no HTTP endpoint for it yet. Staff users belong to one clinic with an `owner`/`admin`/`viewer` role; passwords are scrypt hashes (parameters stored per hash, rehashed on login when raised), sessions are random bearer tokens stored as SHA-256 digests with a 12-hour absolute lifetime, and accounts lock for 15 minutes after five consecutive failures. Disabling a user or changing a password revokes sessions. `audit_events` records staff logins, failures, logouts, password changes and user changes with ids only (no emails, passwords, tokens or IP addresses). Reads scope by tenant and schema foreign keys scope doctor/service writes. Validation responses omit submitted values. Google OAuth refresh tokens and PKCE verifiers are encrypted with AES-256-GCM (random 96-bit nonce, associated data binding each ciphertext to its clinic and row) under an application keyring `TOKEN_ENCRYPTION_KEYS` (`kid:base64-32-byte-key`, first key active, older keys decrypt only, unknown key ids and wrong-length keys rejected). OAuth states are stored only as SHA-256 digests, expire in ten minutes and are single-use; the callback is bound to the state's clinic and starting user, uses PKCE S256, and requires the minimum scopes plus a refresh token. Revocation stops use immediately and clears the ciphertext only after Google confirms the revoke (durable outbox job). Google revocation is grant-wide per Google user and project, so replaced or rejected grants are forgotten locally rather than revoked; owners remove stale grants of other Google users at myaccount.google.com/permissions. Within one clinic, a reconnect cancels disconnect revocations that have not run yet (they would revoke the new grant if it is the same Google user), and the revoke job skips Google when a newer active account exists; a small window remains between that check and Google's response. Known limitation across clinics: the system does not know which Google user an account belongs to (no `openid` scope), so an explicit disconnect in one clinic also disconnects the same Google user's accounts in other clinics (they turn `error`). Follow-up, requiring owner approval of the scope change: request `openid`, verify the id_token, and store a keyed hash of the Google `sub` per account so revocation can be limited or warned about precisely. Cancels use the account that wrote the event, never a newer mapping. Known gaps: the OAuth state is not bound to the browser that started the flow, so an attacker who obtains a started authorization URL (or tricks an admin into opening one) could have a victim's Google consent land in the admin's clinic (consent phishing); when the dashboard session transport is chosen, add an HttpOnly, Secure, SameSite=Lax nonce cookie set at start and checked at the callback. The handling of 403 reasons (only `rateLimitExceeded`/`userRateLimitExceeded` retry; `quotaExceeded` and others are permanent) must be rechecked against live Google documentation and responses before go-live. Provider errors are raised `from None`, which hides the httpx cause but leaves it in `__context__`; any future error reporter (Sentry or similar) must not serialize `__context__`/`__cause__` chains of provider errors, since httpx exceptions carry request URLs with calendar ids. Calendar integration endpoints fail closed (503) without configuration. Tokens, codes, client secrets, provider bodies and calendar ids are never logged, audited, returned or put into exception text; uvicorn access logs drop query strings. `crypto.phone_hash` (HMAC-SHA256 with `PHONE_HASH_KEY`) is available for later phone lookups. Application code does not log request bodies or patient data. The local database binds only to loopback. Source documents, credentials, recordings, and transcripts are ignored by Git.

Bolna gateway (T6, tests only): `/v1/bolna/*` authenticates with the same per-clinic tool credential, which the compiled agent carries as each tool's `api_token` (Authorization header); the compiler receives the token as an argument at provisioning time and never stores it, and its printed/fixture output is redacted. Bolna call-context values (`execution_id`, `from_number`, `agent_id`) are provider-asserted: the docs do not say whether the platform or the LLM writes them into a tool call, so they only scope a conversation, never select a tenant or prove identity. `execution_id` scopes the call session and the server-derived idempotency key; a party holding the clinic's tool credential and an execution id can act within that session, so the credential remains the security boundary. The caller number is stored only as AES-256-GCM ciphertext (associated data `call_session:` + clinic id + session id, key id recorded) plus HMAC-SHA256 under `PHONE_HASH_KEY` (required; 503 when unset); it is never echoed, logged or audited, and the raw number appears in no column. The agent prompt contains `{from_number}` because Bolna's documented substitution needs it there; the prompt forbids reading it aloud, but the LLM provider sees it. The gateway's appointment-status only reports appointments created in or verified by the same call session, and one session can hold at most 3 active appointments. Authentication runs before the duplicate-key check, so unauthenticated requests always get 401. Because Bolna's escaping of `%(name)s` values is unverified, the compiler puts the context fields last in each template and the gateway rejects any body with duplicate JSON keys. The tool routes enforce no IP allowlist; Bolna lists egress addresses 13.203.39.153, 13.126.9.249 and 13.202.133.53 (defense in depth only).

Bolna execution webhooks (T8, tests only; ADR 0007): Bolna documents no webhook signature, no shared secret and no API field for webhook headers (the dashboard's "Add headers" toggle has no documented format), so the clinic's webhook credential (`cvw_` token, scope `webhook`, SHA-256 digest, rotation and revocation as for tool credentials) is the last path segment of the webhook URL. This is a deliberate exception to "no credentials in URLs": the URL lives in Bolna's agent configuration and dashboard, and anything that logs full request paths (reverse proxies, load balancers, APM) sees it. The application's uvicorn access-log filter redacts the segment (`/v1/webhooks/bolna/<redacted>`) and drops query strings; deployment proxies must do the same or not log paths for this prefix, and TLS is mandatory. A leaked URL lets the holder post status events for that clinic only. The worst they can do is mark that clinic's call sessions as ended or final (which ends tool use for that call) or fill disposition codes, for execution ids they already know (the inbox never creates sessions). The clinic is selected only by the credential; the payload `agent_id` is cross-checked against `clinics.bolna_agent_id` when configured (403, nothing stored; T9 also accepts the clinic's `bolna_outbound_agent_id`, whose events are ignored in processing) and against the session's agent id during processing. Malformed and wrong credentials get one 401 with nothing stored. Bodies are capped (`WEBHOOK_MAX_BODY_BYTES`, default 64 KiB, enforced while streaming), duplicate JSON keys are refused, and only an allowlist of ids, status, timestamps, durations, disposition codes and numeric cost is stored: transcripts, summaries, extracted data, recording URLs, phone numbers, context details and error text are dropped before anything is written (tested against the database contents). The optional `BOLNA_WEBHOOK_ALLOWED_IPS` allowlist is defense in depth; X-Forwarded-For is used only when `TRUSTED_PROXY_HOPS` says how many proxies to trust, and then the hops-th address from the right is the client. Reconciliation reads `GET /executions/{id}` with the Bolna API key (`--bolna live`) and keeps the same allowlist. The Bolna account (API key) is shared across clinics and a session's execution id is asserted by whoever holds the clinic's tool credential, so a result is applied only when its agent id equals the clinic's configured `bolna_agent_id`; clinics without one are never polled. With a configured agent id, webhook events that omit `agent_id` are refused at intake and ignored in processing. Repeated X-Forwarded-For lines are combined before the trusted hop is selected, and IPv4-mapped IPv6 peers are normalized. The access-log filter redacts any token of credential shape (`cvt_`/`cvw_`/`cvs_` + 32 hex + `.` + 43 characters) anywhere in the path, and any segment after `/webhooks/<provider>/`, so root-path prefixes, repeated slashes and unrouted paths are covered. Known gap: intake of events for unknown executions is unbounded (each distinct event is stored) until request rate limiting exists.

Patients and verified changes (T7, tests only; ADR 0006): patient names and phones are AES-256-GCM ciphertext under the same keyring with associated data `patient:` + clinic + patient + field, plus the phone HMAC; the phone is copied from the call session, never accepted as a tool argument. Existing bookings are revealed or changed only after `verify-booking` matched both the spoken booking reference (40 random bits, unique per clinic) and the session's caller-number hash; all failure cases share one 404 response, bookings are never enumerated by phone, a shared phone reaches only the reference spoken, and verifications are bound to one session and one appointment. Three distinct failed attempts per session force a staff handoff for verification and changes (attempts are stored as HMAC digests, not references). Cancel/reschedule additionally need `confirmed: true` after a read-back. Attaching a booking to an existing patient by phone + name grants no authority over that patient: consent grants are additive, while a decline (revocation) or a language change is applied only for a patient created in that transaction. Verifying a booking in the call session gives no authority over the matched patient (T9 re-review): a spoofer could attach a booking to a victim's record by caller ID and name, verify it, and then revoke the victim's consent. A decline for a matched existing patient is recorded only as an opt-out of the new booking (ADR 0006, ADR 0008); patient-wide changes are staff only. Unclear consent answers are refused before booking. Staff listings decrypt names and the last two phone digits for owner/admin only and write one audit row per appointment shown; viewers see neither, and full numbers are never returned. Booking references are visible to every staff role, including viewer, and (T9) in the confirmation and reminder SMS text on the patient's phone; reminder call `user_data` does not carry them. A reference plus a spoofed caller ID is what a voice change requires, so treat staff access (and screenshots of the list) accordingly. Reschedule wording risk: the original slot is released in the same transaction that reserves the new one, before calendar sync; if the new event then fails to sync it goes to `needs_review` while the old time may have been rebooked, so the clinic must approve the spoken "moved ... not yet confirmed" wording. Audit rows, outbox payloads, calendar titles (`event_summary`: an opaque appointment-id prefix) and logs carry no names or numbers (tested). Known limits: the phone factor is provider-asserted, so the tool credential remains the boundary (anyone holding it can render any `from_number`); the 3-attempt limit is per call session, with no cross-session rate limit per phone hash or clinic yet; retention defaults (365 days after the last appointment for patients, 90 days for call sessions) are engineering defaults and the purge is operator-run only.

Confirmations and reminders (T9, tests only; ADR 0008): no patient is contacted unless the clinic's `outbound_enabled` is on (default off; owner/admin, audited), the patient has an active consent for that purpose and no opt-out matches. These are re-checked under locks just before each send. Message text is a fixed template (clinic name, date/time, booking reference). It is composed in the worker and passed only to the port, never stored or logged. Booking references are therefore visible in the SMS text (to whoever reads the phone) as well as to every staff role (T7). Reminder call `user_data` carries no booking reference (clinic name, appointment time and an opaque contact reference only): whoever answers an outbound call is unverified, and the reference is what verifies an inbound caller. Reminder rows, outbox payloads, audit rows and logs carry ids, times and short codes only; the phone is decrypted inside the handler at send time. The opt-out tool requires a booking verified in the same call session (reference + caller number), reads the change back unless `confirmed: true`, and never acts on caller ID alone. It is scoped to that one appointment, never patient-wide: verification proves the reference and the caller number, not whose patient record the booking is attached to, and caller ID plus the patient's name can attach a spoofer's new booking to another patient's record (patients.attach). A patient-wide opt-out from such a booking would silence that patient's other bookings, so patient-wide opt-outs are staff only (`POST /v1/admin/appointments/{id}/opt-out`, owner/admin, audited) and the table refuses a patient-wide row from the tool. Staff can undo an opt-out (`.../opt-out/remove`, owner/admin, audited); contacts already suppressed stay suppressed. A booking-scoped opt-out follows a voice reschedule to the new booking. A consent declined at reserve-slot for a matched existing patient never revokes that patient's consent: it becomes an opt-out of that booking only. After an ambiguous timeout a message is reconciled by its stable reference before any new send. A lookup that finds nothing leads to a resend only when the adapter declares both `idempotent_reference` and `consistent_lookup` (provider acceptance criteria, providers/messaging.py); otherwise the contact goes to staff review. A call goes to staff review instead of being redialled. Outcome writes are fenced on the row's attempt count, so a worker that lost its lease mid-send never overwrites a newer attempt.

Reminder calls use a separate Bolna agent (`clinics.bolna_outbound_agent_id`, set with `clinic-voice bolna set-agent --outbound`; a CHECK refuses the inbound agent). Without one, reminder calls are suppressed (`no_outbound_agent`). As defense in depth the tool gateway refuses reserve, verify, cancel, reschedule and opt-out (403, speakable "please call the clinic") on any execution that is a placed reminder call (its execution id matches `reminders.provider_execution_id`) or that names the outbound agent; both values are provider-asserted and only ever used to refuse. The clinic's own phone number is not stored, so calls from it are not detected. Release blocker: the outbound agent's prompt and its tool-free configuration have not been designed or reviewed; an owner must review them (and confirm the agent has no tools) before any clinic enables outbound calls. Webhooks naming the clinic's outbound agent are accepted and ignored (`unknown_execution`); one naming an inbound session's execution id fails the processing agent check and changes nothing. A consent granted after a contact was refused at planning is not backfilled for that already-planned appointment version. Toggling `outbound_enabled` off suppresses every contact that comes due meanwhile permanently (`outbound_disabled`); turning it back on does not revive them. A `daily_contact_budget` of 0 disables outbound contact (`budget_exhausted`). No live messaging provider exists. `--messaging fake` is refused outside `_test`/`_dev` databases.

## Release blockers

This public repository is a development scaffold. Before a pilot implement per-IP/global login rate limiting (account lockout alone lets an attacker who knows an email lock staff out), MFA or an external IdP, a decision on browser session transport (cookies with CSRF protection versus bearer), credential administration audit trail, TLS and request/rate/concurrency limits, trusted proxy configuration, audit trails, verified call identity and anti-replay controls, managed key storage for the token keyring (KMS or secrets manager instead of an environment variable) and a re-encryption job for key rotation, retention/deletion policy, backups/restore drills, monitoring, and access reviews. Plain database storage alone is not appropriate for health or credential data. Use a secrets manager and managed encryption; do not persist raw OAuth tokens in clinic rows.

Bolna tool traffic authenticates with the tool credential in `api_token`; webhooks authenticate with the path credential (custom headers are unverified and unused). An IP allowlist is defense in depth, never the sole credential. Before a pilot, confirm with an owner-authorized test agent that Bolna delivers to the path-token URL unchanged, and configure proxy log redaction for `/v1/webhooks/`. Do not trust arbitrary X-Forwarded-For. Confirm vendor address ranges at deployment; never copy the DOCX's malformed `13.202.133.534`. Do not send production payloads to public webhook debugging services.

Treat speech/transcripts/tool output as untrusted content. Permit only narrowly typed tools. Model claims cannot bypass identity, schedules, state transitions, or authorization. A caller's phone number is not proof of identity. Require verified ownership plus an explicit appointment reference for sensitive operations, with a human fallback for shared phones.

## Information minimization

The system accepts an optional patient name, a preferred language and three consent flags (booking confirmation, reminder call, reminder message), and holds phone numbers only as the call session's and patient's ciphertext plus HMAC. It accepts no age, symptoms, transcript or recording. Purpose: identifying the booking for verified changes and future consented contact. Retention: `clinic-voice retention purge` (not scheduled) deletes patients 365 days (configurable) after their latest appointment and call sessions after 90 days. Before adding any further field document purpose, field-level access, encryption, consent and retention. Calendar entries should use an opaque appointment reference and minimal operational data. Keep credentials/PII out of URLs, logs, trace attributes, exception reports, metrics labels, provider error bodies, and agent config fixtures.

## Clinical and contact policy

The receptionist handles administration only. No diagnosis, medication advice, or medical triage. Have the clinic approve emergency/human-transfer wording and test failed-transfer fallback. Obtain appropriate recording and reminder consent, honor opt-out and quiet hours, and confirm applicable local obligations with qualified reviewers before launch. No legal-compliance certification is asserted by this scaffold.
