# ADR 0011 Chat assistant, staff platform and outbound callbacks

Status: accepted, 31 October 2026 (P2 of [the platform plan](../plans/2026-10-31-platform.md)). Tested against local PostgreSQL with a scripted model (`FakeChatLLM`) and the fake Bolna port only; no model, Bolna or other provider has been called and nothing is deployed.

P2 adds a website chat assistant that can book, the staff screens the web app needs (calendar, staff bookings, callback queue, conversations, stats), and one staff-initiated outbound call per callback request.

Decisions:

- BFF boundary. With `PUBLIC_PROXY_SECRET` set, `/v1/public/*` and `/v1/chat/*` need exactly one `X-Proxy-Secret` (constant-time compare, else 403 `forbidden`), and the client address for rate limits is the BFF's single `X-Client-IP`. This replaces counting `X-Forwarded-For` hops on those paths, which a misconfigured hop count could let a visitor spoof.
- Chat sessions. A session id is 128 random bits shown to the browser only; the table stores its SHA-256. One 404 covers malformed, unknown, closed and chat-disabled sessions. The transcript is kept on the server, encrypted per message with the keyring (AAD `chat_message:<clinic><session><seq>`), as JSON holding the visible text and, for the model's bookkeeping, its tool calls and results. Patients only ever see user and assistant text.
- Model port. `ChatLLMPort` with an OpenAI-compatible adapter (`/chat/completions`, temperature 0.2, `tool_choice` auto), defaulting to Sarvam (`sarvam-105b`, `api-subscription-key` header). Reasoning fields and `<think>` blocks are dropped. Errors are fixed codes (`timeout`, `transport`, `unauthorized`, `http_<status>`, `malformed`); bodies are never logged. Without `CHAT_LLM_API_KEY`, and on any model error, the assistant replies with fixed fallback text and quick replies; a patient never sees a 5xx from the model.
- Tools, not trust. The model sees the clinic profile, hours, services and doctors in the system prompt and may call `clinic_info`, `list_services`, `check_slots`, `propose_booking`, `booking_status` and `request_callback` (at most 4 rounds per turn, then no tools). `propose_booking` only stores a 10-minute `chat_proposals` row after re-checking that the slot is offered. Booking happens only in `POST .../proposals/{id}/confirm`, where the patient types name and phone and ticks consent in a card the web app renders. That confirm goes through the same booking core as the website (`public.create_booking`: new patient row, consents sourced `chat`, `service.reserve`, inline confirm), locks the proposal, books it at most once and replays repeats.
- Emergencies. A narrow phrase match in English, Hindi and Hinglish (bleeding that will not stop, swelling reaching the eye, neck or throat, difficulty breathing or swallowing, fainting, chest pain, accidents and jaw injuries, "this is an emergency") answers with the clinic's approved emergency script when `scripts_approved`, or a default pointing to 112 and the clinic, without calling the model. Booking an "emergency pain visit" is not matched.
- Limits. New sessions and messages per address per hour, turns per conversation, and the web booking buckets on confirm.
- Staff platform. All under `/v1/staff`, clinic from the session. Viewers read; owners and admins write. Decrypted patient details (calendar names, callback details, chat text) are for owners and admins only and every view is audited. The calendar's `sync_state` is derived from the appointment's latest calendar job (`synced`, `pending`, `failed`, `not_applicable`). Staff bookings use the shared booking core with channel `staff`, any active service, and consent only when staff tick it.
- Outbound callbacks. "Call now" places one call per request through the clinic's outbound Bolna agent (never the inbound agent with booking tools) from the new `clinics.bolna_outbound_from_number`. It obeys the reminder contact policy: outbound switch, synthetic guard, quiet hours, and the daily budget it shares with reminders (`callback_requests.call_contact_day` is counted by `reminders.budget_used`). The decision and the `calling` mark commit under the budget lock, the request row and the clinic row (in that order), before the provider call runs with the connection idle. A repeated click never dials again. A timeout keeps the request `calling` with outcome `unknown` and is never retried automatically, because Bolna offers no lookup by client reference. A definite failure reopens the request and releases the budget slot.
- Synthetic guard. Migration 019 adds `synthetic` to patients and callback requests. The seed marks everything it writes and grants no consent; reminders, confirmations and callback calls refuse synthetic targets (`synthetic_contact`), including a request whose phone matches a seeded patient.
- Retention. Chat sessions (with messages and proposals) are deleted after `RETENTION_SESSION_DAYS` of inactivity; purged patients are unlinked from sessions.

Consequences: the web app must render the proposal card and send name, phone and consent itself; the model never sees them. A clinic must set an outbound caller number (owner) and an outbound agent before "Call now" works, and `outbound_enabled` stays off by default. Voice conversations have no stored transcript, so the staff view shows the call summary and linked appointments only. Calls whose outcome is unknown need a staff resolution.
