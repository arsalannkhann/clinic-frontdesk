# ADR 0011 Chat assistant, staff platform and outbound callbacks

Status: accepted, 31 October 2026 (P2 of [the platform plan](../plans/2026-10-31-platform.md)). Tested against local PostgreSQL with a scripted model (`FakeChatLLM`) and the fake Bolna port only; no model, Bolna or other provider has been called and nothing is deployed.

P2 adds a website chat assistant that can book, the staff screens the web app needs (calendar, staff bookings, callback queue, conversations, stats), and one staff-initiated outbound call per callback request.

Decisions:

- BFF boundary. With `PUBLIC_PROXY_SECRET` set, `/v1/public/*` and `/v1/chat/*` need exactly one `X-Proxy-Secret` (constant-time compare, else 403 `forbidden`), and the client address for rate limits is the BFF's single `X-Client-IP`. This replaces counting `X-Forwarded-For` hops on those paths, which a misconfigured hop count could let a visitor spoof.
- Chat sessions. A session id is 128 random bits shown to the browser only; the table stores its SHA-256. One 404 covers malformed, unknown, closed and chat-disabled sessions. The transcript is kept on the server, encrypted per message with the keyring (AAD `chat_message:<clinic><session><seq>`), as JSON holding the visible text and, for the model's bookkeeping, its tool calls and results. Patients only ever see user and assistant text.
- Session id in the URL path (accepted, documented). The routes keep the bearer session id as a path segment (`/v1/chat/sessions/{id}/...`), as the web app already calls them. The application's access log redacts it (`api.redact_path`, which stays), but every hop outside the application that logs request paths records it in clear: Vercel's and the BFF's platform request logs, any CDN, proxy, load balancer or APM in front of the API. Anyone who can read those logs can read and continue the conversation for the session's lifetime (it cannot reveal other patients' data or confirm a booking without the patient's name and phone). Mitigations: keep platform log access to operators, keep log retention short, and do not forward paths under `/v1/chat/sessions/` to third-party log sinks; moving the id to a header would change the BFF contract and is deferred.
- Model port. `ChatLLMPort` with an OpenAI-compatible adapter (`/chat/completions`, temperature 0.2, `tool_choice` auto), defaulting to Sarvam (`sarvam-105b`, `api-subscription-key` header). Reasoning fields and `<think>` blocks are dropped, including one never closed (everything after an unclosed `<think>`). A reply stopped by `max_tokens` (`finish_reason` `length`) with no visible text and no tool call is a failure (`length`); tool calls of a truncated reply still run. Errors are fixed codes (`timeout`, `transport`, `unauthorized`, `http_<status>`, `malformed`, `length`); bodies are never logged. Without `CHAT_LLM_API_KEY`, and on any model error, the assistant replies with fixed fallback text and quick replies; a patient never sees a 5xx from the model.
- Tools, not trust. The model sees the clinic profile, hours, services and doctors in the system prompt and may call `clinic_info`, `list_services`, `check_slots`, `propose_booking`, `booking_status` and `request_callback` (at most 4 rounds per turn, then no tools). `propose_booking` only stores a 10-minute `chat_proposals` row after re-checking that the slot is offered. Booking happens only in `POST .../proposals/{id}/confirm`, where the patient types name and phone and ticks consent in a card the web app renders. That confirm goes through the same booking core as the website (`public.create_booking`: new patient row, consents sourced `chat`, `service.reserve`, inline confirm), takes the clinic row FOR SHARE (level 1b, as the web gate does) and then the proposal row FOR UPDATE (level 1c, locks.py), re-checks that the service is still publicly offered (`public.OFFERED`; one hidden since the proposal is 409 `slot_unavailable`), books it at most once and replays repeats.
- One turn at a time. A session answers one message at a time; a concurrent send is 409 `turn_in_progress`. We use a busy lease, not a lock: `chat_sessions.busy_until` (migration 020) is set when the user message is stored and cleared (compare-and-set on its value) when the reply is stored. A per-session transaction-scoped advisory lock held across the turn was rejected because a turn spans model calls of up to `CHAT_LLM_TIMEOUT_SECONDS` (25 s) each, so it would keep a pooled transaction, and with transaction pooling a server connection, open for the whole turn; session-level locks do not work through the pooler at all. The lease is `max(60 s, timeout + 20 s)`, a turn starts a further model call only while it fits inside the lease, and a crashed turn frees the session when the lease ends.
- Emergencies. A narrow phrase match in English, Hindi (Devanagari, either nukta form) and Hinglish (bleeding that will not stop, with "stop" up to about 30 characters from "bleeding" in either order, including "hasn't stopped" and "won't stop"; swelling reaching the eye, neck or throat, or with a high fever; difficulty breathing or swallowing; fainting; chest pain; injuries such as a knocked-out tooth, a jaw injury, "fell and broke" or a road accident, never a bare "accident"; "this is an emergency") answers with the clinic's approved emergency script when `scripts_approved`, or a default pointing to 112 and the clinic, without calling the model. Booking an "emergency pain visit" and "I booked the wrong day by accident" are not matched (table-tested positives and negatives).
- Limits. New sessions, messages and transcript reloads per address per hour (an IPv6 address counts by its /64), turns per conversation, model calls per clinic per day (`CHAT_LLM_CALLS_PER_CLINIC_PER_DAY`, then the fallback reply), and the web booking buckets on confirm. A reload returns the newest 100 visible messages; the staff calendar returns at most 2000 appointments (`truncated`), and list views write their detail-view audit rows in one insert.
- One connection per turn. A turn reuses one database connection for the session check, every tool call, its stores and the release; each use is its own committed transaction, so the connection is idle (never inside a transaction, no server connection held through a transaction pooler) while the model is called.
- Staff platform. All under `/v1/staff`, clinic from the session. Viewers read; owners and admins write. Decrypted patient details (calendar names, callback details, chat text) are for owners and admins only and every view is audited. The calendar's `sync_state` is derived from the appointment's latest calendar job (`synced`, `pending`, `failed`, `not_applicable`). Staff bookings use the shared booking core with channel `staff`, any active service, and consent only when staff tick it.
- Outbound callbacks. "Call now" places one call per request through the clinic's outbound Bolna agent (never the inbound agent with booking tools) from the new `clinics.bolna_outbound_from_number`. It obeys the reminder contact policy: outbound switch, synthetic guard, quiet hours, and the daily budget it shares with reminders (`callback_requests.call_contact_day` is counted by `reminders.budget_used`). The decision and the `calling` mark commit under the budget lock, the request row and the clinic row (in that order), before the provider call runs with the connection idle. A repeated click never dials again. A timeout, or any other unexpected exception from the port, keeps the request `calling` with outcome `unknown` and is never retried automatically, because Bolna offers no lookup by client reference. Owners and admins can reopen a placed or unknown call (`POST /v1/staff/callbacks/{id}/reopen`, audited) to retry it deliberately; the earlier call stays counted against its day's budget (`callback_call_attempts`, migration 020). A definite failure reopens the request and releases the budget slot.
- Synthetic guard. Migration 019 adds `synthetic` to patients and callback requests. The seed marks everything it writes and grants no consent; reminders, confirmations and callback calls refuse synthetic targets (`synthetic_contact`), including a request whose phone matches a seeded patient.
- Retention. Chat sessions (with messages and proposals) are deleted after `RETENTION_SESSION_DAYS` of inactivity; purged patients are unlinked from sessions.

Consequences: the web app must render the proposal card and send name, phone and consent itself; the model never sees them. A clinic must set an outbound caller number (owner) and an outbound agent before "Call now" works, and `outbound_enabled` stays off by default. Voice conversations have no stored transcript, so the staff view shows the call summary and linked appointments only. Calls whose outcome is unknown need a staff resolution: resolve, or reopen and call again.
