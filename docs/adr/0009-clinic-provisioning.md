# ADR 0009 Clinic provisioning state machine

Status: accepted, 29 October 2026.

T10 turns clinic onboarding into a recoverable state machine that creates the clinic's inbound Bolna agent, routes an existing number to it and verifies the result. No live Bolna call has been made; everything is tested against FakeBolna and httpx.MockTransport.

Decisions:

- One row per clinic, one step per job. `provisioning` (migration 015) holds state, `resume_state`, agent id and name, the tool credential id, the owner-selected `phone_number_id`, per-step attempt counters, a short `last_error` and `version`. `POST /v1/admin/provisioning/advance` (owner) enqueues one `provision.step` job carrying the current version; a unique partial index allows at most one pending or processing step per clinic, and advance returns 409 otherwise. Steps run only on a worker with a Bolna port (`provision.step` joins the Bolna-only kinds). We chose explicit per-step advances over one job running the whole chain so the owner sees and approves each provider write.
- Version fencing. `version` grows on every state change, number selection, reset and activation. A job acts only while the row has its version; the final transaction re-checks version and state under the row lock after taking its fenced outbox row. Number selection, reset and activation are refused while a step is in flight, so a step never acts on a number or state that changed underneath it. Dead `provision.step` jobs are not requeued through the outbox route (409); reset and advance re-check everything.
- Deterministic agent name and lookup. The agent is named `clinic-<full clinic id hex>-v1` (the full id, since the Bolna account is shared). The step looks it up by stored agent id (`GET /v2/agent/{id}`), else by name (`GET /v2/agent/all`, added to `BolnaPort` as `get_agent`/`list_agents` after rechecking the docs), and updates a found agent with a full PUT instead of creating another. Before a create it commits `agent_create_pending` (write intent). After a timeout, a malformed 2xx or a crash, the next attempt reconciles by name. If the port has no lookup, or the lookup found nothing and the adapter does not declare `consistent_agent_lookup` (BolnaClient: False, because Bolna documents no read-after-write guarantee), the step goes to manual_review rather than risk a second agent. Two agents with the name are ambiguous (manual_review). A hand-set `clinics.bolna_agent_id` is never replaced (manual_review `agent_preconfigured`).
- Tool credential. Each agent attempt issues a fresh tenant tool credential (label `provisioning:agent`) in the same fenced transaction that records its id and the write intent; the plaintext exists only in the in-memory payload compiled by `agent_config` and sent to Bolna. Plaintext cannot be recovered later, so a reconciled agent is updated with a new credential rather than reused. After an acknowledged write, the clinic's other `provisioning:agent` credentials are revoked. Residual: a worker that lost its lease could land a late PUT with its (now revoked) credential after a newer attempt; verify then sees a credential mismatch where the token is readable.
- Numbers. The owner selects an existing number id; it must appear in `GET /phone-numbers/all` and not be routed to another agent (refusals keep the state with `number_not_in_account` / `number_in_use`). `POST /inbound/setup` is treated as idempotent: a timeout retries and the next attempt recognizes the assignment from the listing. A number id and an agent id belong to at most one clinic (unique indexes). There is no purchase path.
- Verification reads back the agent (id, name, every expected tool URL, and the credential id where the token is readable) and the number's routing. Bolna may mask `api_token` in responses (undocumented); then the event outcome is `token_unchecked` rather than `ok`. Mismatches go to manual_review with `resume_state` set to the step that repairs them (agent or number).
- Errors. ProviderPermanent goes to failed (`unauthorized` or `provider_permanent`); a 4xx on create clears the write intent. Timeouts and retryable errors retry with the outbox backoff. More than six runs of one step, or a dead-lettered job (on_dead), go to manual_review `retries_exhausted`. Configuration gaps (`gateway_unconfigured`, `agent_config_invalid`) fail.
- Reset (owner) moves failed or manual_review back to `resume_state`, clears the error, the attempt counters and the write intent. It is the owner's assertion that the provider state was checked (OPERATIONS.md lists what to check per code).
- Activation (owner) needs verified, a connected calendar, the provisioned agent still recorded as `clinics.bolna_agent_id`, and approved, non-empty emergency and handoff scripts. The scripts are new clinic fields (`emergency_text`, `handoff_text`, `scripts_approved`, editable by owner and admin); editing a text clears approval unless the same request approves it, and a CHECK refuses approval of an empty text. Activation does not change `outbound_enabled`.
- History. `provisioning_events` is append-only (a trigger rejects UPDATE and DELETE) and holds from/to state, step, outcome code and the staff actor (null for the worker). Staff mutations are also audited with ids only.
- Outbound agent not provisioned. The tool-free reminder agent stays a manual owner step (`bolna set-agent --outbound`), because its prompt and tool-free configuration still need owner review (ADR 0008).

Consequences: an ambiguous create on the live client always needs a human check, by design. Nothing reads the `active` state yet: the gateway does not refuse tool calls for clinics that are not active, and calls can reach the agent from the number step on. The context tool still serves placeholder emergency text; serving the approved scripts is a follow-up. Rotating the credential of an active agent, re-provisioning (a `-v2` agent) and the outbound agent remain manual.
