# ADR 0009 Clinic provisioning state machine

Status: accepted, 29 October 2026; amended the same day after the T10 spec review (migration 015 edited before release) to gate the gateway on the state, and again after the T10 security review (agent conflicts, kept create intent, credential checks, in-transaction gating, manual-setup cutover).

T10 turns clinic onboarding into a recoverable state machine that creates the clinic's inbound Bolna agent, routes an existing number to it and verifies the result. No live Bolna call has been made; everything is tested against FakeBolna and httpx.MockTransport.

Decisions:

- One row per clinic, one step per job. `provisioning` (migration 015) holds state, `resume_state`, agent id and name, the tool credential id, the owner-selected `phone_number_id`, per-step attempt counters, a short `last_error` and `version`. `POST /v1/admin/provisioning/advance` (owner) enqueues one `provision.step` job carrying the current version; a unique partial index allows at most one pending or processing step per clinic, and advance returns 409 otherwise. Steps run only on a worker with a Bolna port (`provision.step` joins the Bolna-only kinds). We chose explicit per-step advances over one job running the whole chain so the owner sees and approves each provider write.
- Version fencing. `version` grows on every state change, number selection, reset and activation. A job acts only while the row has its version; the final transaction re-checks version and state under the row lock after taking its fenced outbox row. Number selection, reset and activation are refused while a step is in flight, so a step never acts on a number or state that changed underneath it. Dead `provision.step` jobs are not requeued through the outbox route (409); reset and advance re-check everything.
- Deterministic agent name and lookup. The agent is named `clinic-<full clinic id hex>-v1` (the full id, since the Bolna account is shared). The step looks it up by stored agent id (`GET /v2/agent/{id}`), else by name (`GET /v2/agent/all`, added to `BolnaPort` as `get_agent`/`list_agents` after rechecking the docs), and updates a found agent with a full PUT instead of creating another. Before a create it commits `agent_create_pending` (write intent). After a timeout, a malformed 2xx or a crash, the next attempt reconciles by name. If the port has no lookup, or the lookup found nothing and the adapter does not declare `consistent_agent_lookup` (BolnaClient: False, because Bolna documents no read-after-write guarantee), the step goes to manual_review rather than risk a second agent. Two agents with the name are ambiguous (manual_review). A hand-set `clinics.bolna_agent_id` is never replaced (manual_review `agent_preconfigured`). The account is shared, so a found agent (by id or name) is refused before any credential is issued or write sent (manual_review `agent_conflict`) when it is this clinic's outbound agent or any other clinic's provisioned, inbound or outbound agent. The same check runs again after the write, under the row lock: a created id that belongs elsewhere goes to review and that attempt's credential is revoked. `clinics.bolna_agent_id` is set by compare-and-set against the value read before the write (`IS NOT DISTINCT FROM`), so a concurrent `bolna set-agent` is never overwritten (mismatch: `agent_conflict`). `list_agents` returns every agent of the account in one response (no pagination or name filter is documented), parsed in memory under the 1 MiB response cap; items without a usable id are skipped. An account with more agents than fit in 1 MiB makes the lookup fail retryably and end in review.
- Tool credential. Each agent attempt issues a fresh tenant tool credential (label `provisioning:agent`) in the same fenced transaction that records it as `attempt_credential_id` with the write intent; the plaintext exists only in the in-memory payload compiled by `agent_config` and sent to Bolna. Plaintext cannot be recovered later, so a reconciled agent is updated with a new credential rather than reused. An acknowledged write makes it `tool_credential_id` and revokes the clinic's other `provisioning:agent` credentials. A write Bolna refused (4xx) or that was never sent gives its credential up; when a step ends in failed or manual_review, every provisioning credential except `tool_credential_id` and a possibly delivered `attempt_credential_id` (timed-out write) is revoked. Residual: a worker that lost its lease could land a late PUT with its (now revoked) credential after a newer attempt; verify then sees a credential mismatch where the token is readable.
- Numbers. The owner selects an existing number id; it must appear in `GET /phone-numbers/all` and not be routed to another agent (refusals keep the state with `number_not_in_account` / `number_in_use`). `POST /inbound/setup` is treated as idempotent: a timeout retries and the next attempt recognizes the assignment from the listing. A number id and an agent id belong to at most one clinic (unique indexes). There is no purchase path.
- Verification first requires `tool_credential_id` to be unrevoked and unexpired (else manual_review `credential_inactive`, resume at the agent step), then reads back the agent (id, name, every expected tool URL, and the credential id of each token) and the number's routing. Bolna may mask `api_token` in responses (undocumented): only a true mask (asterisks, optionally after `Bearer `) counts, and then the event outcome is `token_unchecked` rather than `ok`. An absent token or one that is not a tool credential is `credential_mismatch`. Activation re-checks that the credential is active. Mismatches go to manual_review with `resume_state` set to the step that repairs them (agent or number).
- Errors. ProviderPermanent goes to failed (`unauthorized` or `provider_permanent`); a 4xx on a write leaves any earlier unresolved write intent as it was. Timeouts and retryable errors retry with the outbox backoff. Provider writes and provider errors count toward a budget of six per step; refusals (calendar not ready, number not in the account or in use) and successful reads do not, so an owner fixing setup is never pushed into review. A step at its budget, or a dead-lettered job (on_dead), goes to manual_review `retries_exhausted`. Configuration gaps (`gateway_unconfigured`, `agent_config_invalid`) fail.
- Reset (owner) moves failed or manual_review back to `resume_state` and clears the error and the attempt counters. It keeps an ambiguous create intent (`agent_create_pending`), so the next agent step still refuses to create while the lookup cannot prove absence. Clearing it takes an explicit owner confirmation, `{"confirm_no_stray_agent": true}`, accepted only after `create_uncertain` or `lease_lost` (a dead-lettered step whose lease expired); it also revokes the credential the lost write may have delivered. A dead-letter maps the outbox `lease_expired` code to `lease_lost`, others to `retries_exhausted`. Every attempt count is fenced on the job's lease as well as the row version.
- Line gating. The Bolna gateway checks the provisioning state after authentication and before any write: context and read-only tools (check-slots, appointment-status, verify-booking) from `verified`, booking-changing tools (reserve-slot, cancel-booking, reschedule-booking, opt-out) only when `active`, or in `verified` while the owner-only, audited `clinics.test_calls_enabled` is on, so the owner can place test calls before activation. Every other state, and a clinic with no provisioning row, gets a speakable 403 "this line isn't accepting bookings yet" and no call session. verify-booking is read-only for this purpose, though it counts verification failures. Booking-changing tools re-check the line inside their write transaction, holding the clinic row FOR SHARE (lock level 1b); every change that closes the line updates the clinic row, so no booking write commits after the line closed. Clinics configured by hand get a row from the operator CLI `clinic-voice provisioning activate-manual`, which checks the prerequisites that still apply (calendar ready, scripts approved, `bolna_agent_id` set and not used elsewhere, no row or only an untouched draft row), writes state `active` with the hand-set agent id and no number id (the CHECK requiring a number id no longer covers `active`), and records a `manual_activation` event with no actor. It verifies nothing at Bolna: the operator vouches for the hand configuration. Owner provisioning routes on a clinic with a hand-set agent and no row return 409 "Manual setup: use clinic-voice provisioning activate-manual" and create no row, so they cannot block it.
- Approved scripts are served. The context tool returns the clinic's `emergency_text` and `handoff_text` with `approved_text: true` once approved; until then placeholders with `approved_text: false`. `faq_text` stays a placeholder. Only an owner sets `scripts_approved`; an admin may edit the texts, which clears approval.
- Activation (owner) needs verified, a connected calendar, the provisioned agent still recorded as `clinics.bolna_agent_id`, and approved, non-empty emergency and handoff scripts. The scripts are new clinic fields (`emergency_text`, `handoff_text`, `scripts_approved`, editable by owner and admin); editing a text clears approval unless the same request approves it, and a CHECK refuses approval of an empty text. Activation does not change `outbound_enabled`.
- History. `provisioning_events` is append-only (a trigger rejects UPDATE and DELETE) and holds from/to state, step, outcome code and the staff actor (null for the worker). Staff mutations are also audited with ids only.
- Outbound agent not provisioned. The tool-free reminder agent stays a manual owner step (`bolna set-agent --outbound`), because its prompt and tool-free configuration still need owner review (ADR 0008).

Consequences: an ambiguous create on the live client always needs a human check, by design. Calls can reach the agent from the number step on, but the gateway refuses them until `verified` and refuses booking changes until `active` (or owner test calls). Cutover: a clinic configured by hand before T10 has no provisioning row, so its line goes dark from the moment migration 015 is applied until its emergency and handoff scripts are approved by an owner and an operator runs `activate-manual`; the scripts columns are new, so this cannot be prepared before the migration. Plan the upgrade per clinic in a quiet window. A read-only tool racing a line change may see either side; booking writes cannot (in-transaction re-check). Rotating the credential of an active agent, re-provisioning (a `-v2` agent) and the outbound agent remain manual.
