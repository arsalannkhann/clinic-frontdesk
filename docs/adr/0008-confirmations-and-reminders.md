# ADR 0008 Confirmations, reminders and opt-out

Status: accepted, 29 October 2026; amended the same day after the T9 security review (migration 014 edited before release).

T9 adds booking confirmation messages, reminder calls and reminder messages, quiet hours, a daily contact budget and opt-outs. Patient messaging and outbound calls need explicit owner authorization (AGENTS.md), and no messaging provider has been chosen, so everything here is built and tested against fakes and is off by default.

Decisions:

- Off by default, per clinic. `clinics.outbound_enabled` (migration 014) is false. Nothing is planned or sent for a clinic until an owner or admin enables it through `PATCH /v1/admin/clinic`, and each send checks it again. Enabling and disabling are audited separately (`clinic.outbound_enabled` / `clinic.outbound_disabled`). The worker contacts nobody without a port for the channel: `--messaging fake` is the only messaging option and, like the other fakes, is refused outside `_test`/`_dev` databases unless `APP_ENV=development`. Reminder calls use `--bolna` (fake or live). With `--bolna live`, enabling `outbound_enabled` places real calls, so it needs the owner's authorization first.
- No live messaging provider. `providers/messaging.py` defines `MessagingPort` (`send_message(to, body, reference)`, `get_message(reference)`, and two declared capabilities `idempotent_reference` and `consistent_lookup`) and its adapter obligations, plus `FakeMessaging` (both capabilities on by default, configurable for tests). `check_ports` refuses an adapter that does not declare both as booleans. The capabilities are provider acceptance criteria: each must be proven from official documentation and contract fixtures before an adapter sets it True. Choosing a provider, recording its documentation and writing a contract-tested adapter is an owner action.
- One row per planned contact. `reminders` holds each confirmation, reminder call or reminder message of one appointment version. It records the channel, purpose, planned time, clinic-local `contact_day`, status, attempts, a short code, a stable `provider_reference` (`cvr_<id hex>`) and the provider execution or message id. It never holds a message body, number or name. `dedupe_key` (appointment, version, channel, purpose, lead minutes) is unique per clinic, so racing planners create a contact once and several kinds per appointment stay possible. Only the planner whose insert won adds the job (`notification.send` for messages, `reminder.call` for calls, payload `{reminder_id}`). One job per reminder is a unique index. Migration 014 narrows the old per-(appointment, kind, version) uniqueness to exclude these two kinds.
- Planned when the appointment is confirmed. The calendar.create handler's confirming transaction calls `reminders.on_confirmed`. A confirmation message is planned for now, and a reminder for `starts_at - reminder_lead_minutes` (default 24 h) per consented channel. Each needs an active consent for its purpose (`booking_confirmation`, `reminder_call`, `reminder_message`) and no matching opt-out. A contact refused by policy at planning (no consent, opted out) is stored as `suppressed` with the reason and no job, so it is never planned again for that version; a consent granted later therefore applies from the next version (reschedule), not to an already-refused contact. A reminder whose lead time has already passed is not planned. The confirmation covers it. Worker housekeeping (`reminders.schedule_due`) backfills reminders for confirmed appointments that enter the reminder window without one, for example after outbound was enabled. Its candidates are ordered by reminder time and exclude channels the patient has no consent for or opted out of, so every candidate gets a row and drops out: refused appointments cannot fill the batch and starve later ones. Both planners take a per-appointment advisory planning lock and skip a channel that already has a reminder for that version with any lead time, so a lead-time edit cannot plan a second reminder; the dedupe key still makes concurrent planners with the same lead safe. Planning in the confirming transaction runs in a savepoint and logs only the error type, so a planning error never blocks the confirmation (housekeeping backfills the reminders; that confirmation message is lost).
- Quiet hours and DST. `quiet_hours_start`/`end` (default 21:00-09:00, clinic-local, start after end wraps midnight, start = end refused) are evaluated on the clinic's IANA zone. A contact inside the window moves to the next allowed instant. The end wall time is resolved with both DST folds and the earliest allowed instant wins. An ambiguous end takes its first occurrence. An end that does not exist (spring forward) lands at most one hour after the transition. A contact is never moved later than 30 minutes before the appointment (`MIN_NOTICE`). If no allowed time fits, it is stored as `suppressed`/`quiet_hours`. The handler re-checks quiet hours at send time (settings may have changed) and defers its job without spending an attempt (`outbox.defer`).
- Daily budget. `daily_contact_budget` (default 200; 0 disables outbound contact) caps contacts per clinic-local day. The next day starts at the earliest instant whose local date is that day, so a zone whose midnight does not exist (America/Santiago, America/Havana) still moves forward. Planning counts contacts planned for the day. Sending counts contacts attempted that day, under a per-(clinic, day) advisory lock, which is the strict check. An over-budget contact is postponed to the next allowed time of the next day with room, within its window. Otherwise it is `suppressed`/`budget_exhausted`. It is never dropped silently. Confirmations count too.
- Re-check before contact. In one transaction a send locks the appointment (FOR SHARE), the budget day, the reminder row and the clinic row (FOR SHARE), and re-reads the clinic's settings under those locks (lock order in `locks.py`), so a settings change either lands before the checks or waits until the contact is marked `sending`. It re-checks the appointment status and version, the start time, expiry (12 h after the planned time), `outbound_enabled`, quiet hours, the budget, consent and opt-out. Turning `outbound_enabled` off suppresses contacts that come due meanwhile permanently; turning it on again does not revive them. It then marks the row `sending` and checks its own fence while renewing its lease. Only then does it decrypt the phone and send with the connection idle. A stale version cancels the contact (`stale`). Policy outcomes are `suppressed` with a reason code.
- Cancellation and reschedule. `appointments.cancel_locked` (staff cancel, voice cancel and reschedule, review resolution) cancels the old version's unsent contacts in the same transaction. If that version has any contact, it also enqueues `reminder.stop`. The job sweeps unsent contacts again, defers (no attempt spent) while a call is `sending`, and calls `BolnaPort.stop_scheduled_call` by execution id for each placed call without a stop outcome. A refused stop is recorded as `not_stoppable` unless a lookup shows the call was already stopped. A reschedule's new appointment gets its own contacts when it is confirmed. There is one `reminder.stop` per appointment version: an opt-out that covers calls enqueues it too (payload `reason: opted_out`, which only stops placed calls), and a later cancellation of that version shares it. A dead stop job moves its unstopped calls to `needs_review` (`stop_failed`; the row keeps `sent_at`).
- Calls are placed when due, not provider-scheduled. The worker calls `POST /call` without `scheduled_at` at the planned time, so consent, opt-out and cancellation are re-checked at the last moment. `stop_scheduled_call` therefore matters only for a call Bolna has queued but not yet started. The call carries `user_data` with the clinic name, appointment time and our contact reference only: no booking reference, because whoever answers is unverified and the reference is what verifies an inbound caller. It uses a separate agent, `clinics.bolna_outbound_agent_id` (CLI `bolna set-agent --outbound`; a CHECK refuses the inbound `bolna_agent_id`), never the inbound agent whose tools book, verify, change and opt out. Without an outbound agent, reminder calls are suppressed (`no_outbound_agent`). As defense in depth the gateway refuses reserve, verify, cancel, reschedule and opt-out on executions that are placed reminder calls (execution id) or name the outbound agent, with a speakable "please call the clinic" 403; the clinic's own number is not stored, so it is not used. The outbound agent's prompt, wording and tool-free configuration are not designed here: an owner review of them is a release blocker before any clinic enables outbound calls.
- Ambiguous outcomes. A timeout (or unclassified provider error) on a send marks the contact `unknown`. Before anything else, the next attempt reconciles a message through `get_message(provider_reference)`. If the message is found, the contact is sent. If it is not found and the adapter declares both `idempotent_reference` and `consistent_lookup`, nothing was sent (and a duplicate send would be deduplicated), so the contact is attempted again under the same reference. Otherwise "not found" proves nothing (the lookup may lag, or a resend may deliver twice): the contact goes to `needs_review` (`lookup_not_found`) and is never resent automatically. If the lookup fails, the contact stays unknown and the attempt retries later. Bolna documents no lookup by client reference, and a timed-out `POST /call` returns no execution id. A call timeout therefore goes straight to `needs_review` (staff: `GET /v1/admin/reminders?status=needs_review`) and is never redialled. A `sending` row found by a new attempt (the worker died mid-send) is treated as `unknown`. Retryable errors return the row to `scheduled`. Permanent errors mark it `failed` and dead-letter the job. Every outcome write is fenced on the row's status and attempt count, so a worker that lost its lease mid-send records its outcome only if no newer attempt or reconciliation has moved the row. A dead contact job moves an unsettled row to `needs_review` and an unsent one to `failed`. Housekeeping (`reminders.sweep_lost`) moves a `scheduled` or `sending` row whose job is done, dead or missing to `needs_review` (`job_lost`) after 10 minutes. Requeueing a job does not re-contact.
- Opt-out requires verification and is scoped to the verified booking. `POST /v1/bolna/tools/opt-out` applies only to a booking this call session verified (booking reference plus caller number, ADR 0006), reads the change back unless `confirmed: true` (as cancel does), and never applies to the caller's number alone. It covers that one appointment, not the patient: verification proves the reference and the caller number, not whose patient record the booking belongs to, and caller ID plus the patient's name attaches a new booking to an existing patient record (patients.attach). A spoofer could therefore book, verify their own new booking and, with a patient-wide opt-out, silence the victim's other bookings. We chose to keep patient-wide opt-out staff only rather than allow it when the verified appointment created the patient row: that rule would still need care for records later reused by attach, and a booking-scoped opt-out covers what a caller can prove. `contact_preferences.appointment_id` NULL is patient-wide and allowed only for staff (CHECK); otherwise the opt-out matches that appointment's contacts only. Unverified sessions get a speakable 403 that points to verification or staff. Staff can opt a patient out patient-wide through `POST /v1/admin/appointments/{id}/opt-out` and undo an opt-out through `POST /v1/admin/appointments/{id}/opt-out/remove` (owner, admin; both audited with the appointment id). An opt-out suppresses the matching unsent contacts in the same transaction and blocks later planning and sending; an undo does not revive suppressed contacts.
- Webhook opt-out is a hook only. Bolna documents no opt-out field or disposition value, and the stored disposition codes are not documented vocabularies. `bolna.webhooks.disposition_opts_out` therefore always returns False, and nothing is inferred from free text or `extracted_data` (never stored).
- T7 review fold-in. When an unverified caller declines a purpose that has an active grant, the decline is still not applied. The reserve-slot `spoken` text now adds that changing an existing preference needs verification on the call or clinic staff.

Consequences: no live patient contact is possible without a messaging adapter (none exists), `--bolna live` and an owner or admin enabling outbound for the clinic. Outbound reminder executions create no call session, and webhooks naming the outbound agent fail the inbound-agent cross-check (403), so their final call status is not tracked yet. Booking tools are refused on reminder calls, so callees who say "stop" on a reminder call must call the clinic or be handled by staff until a contract-tested mechanism exists. Budget counts are per clinic-local day and assume the clinic timezone does not change between planning and sending.
