# ADR 0010 Platform foundation: public API, ledger calendar, worker tick, Supabase and Vercel

Status: accepted, 31 October 2026 (P1 of [the platform plan](../plans/2026-10-31-platform.md)). Tested against local PostgreSQL only; nothing has been deployed to Supabase or Vercel and no provider has been called.

P1 lets one backend serve a public clinic website and chat alongside voice, on Supabase Postgres (through the transaction pooler) and Vercel serverless functions, without a long-running worker.

Decisions:

- Pooler-safe connections. `db.connect` sets `prepare_threshold=None` when the URL uses port 6543 (Supabase's transaction pooler), or when the process environment sets `DATABASE_POOLER=transaction`. `session` and `none` force it off. Audit: the code takes only transaction-scoped advisory locks (`pg_advisory_xact_lock`), never runs `SET` without `LOCAL`, and uses no `LISTEN`, temporary tables or named cursors, so nothing depends on session state. A test greps the source for these. Migrations need DDL in one session, so they run over a direct or session-pooler connection, never the transaction pooler.
- Migration 018 hardening. Every table in `public` gets `ENABLE ROW LEVEL SECURITY` with no policies. The backend connects as the table owner, which bypasses RLS, so this changes nothing for it. Supabase's PostgREST roles (`anon` and `authenticated`), however, can read nothing. A DO block guarded by `pg_roles` revokes all table, sequence and function privileges from those roles, together with their default privileges; on plain PostgreSQL it does nothing. `FORCE ROW LEVEL SECURITY` is deliberately not used, because it would subject the owner to RLS too. Later migrations that add tables must enable RLS, and a test checks `relrowsecurity` on every table.
- Ledger calendar. A doctor whose `booking_calendar_id` is `ledger:<doctor id>` (a CHECK constraint ties the id to its own doctor) uses the database as their calendar. `LedgerCalendar` derives events from the `appointments` row (event id, calendar id, version, status). `insert_event` acknowledges, `cancel_event` is a no-op, and `free_busy` is empty, because the appointment rows and the exclusion constraint are already the busy state. The outbox, fencing and confirmation path stay exactly as they are for Google. `LedgerResolver` wraps the Google resolver: it routes by calendar-id prefix, so a job created before a doctor was remapped still goes to the calendar that holds its event. Ledger is a production mode; `worker --calendar ledger` is not refused outside development.
- Worker tick. `POST /v1/internal/worker/tick`, authorised by `Bearer WORKER_TICK_SECRET` compared in constant time, runs `run_batch` (the same claim, lease and fenced completion as the worker) in batches of 5 until `WORKER_TICK_BUDGET_SECONDS` (default 8) runs out. Claimed jobs that have not started are released, and bounded housekeeping then runs. The response holds counts only. The route returns 404 while the secret is unset. It is meant for Supabase pg_cron through pg_net, every minute. The tick builds its ports from settings: the ledger, plus Google when configured, and Bolna when `BOLNA_API_KEY` is set. It has no messaging port, so messaging jobs stay pending.
- Inline confirm. After a public booking commits, the request claims that booking's own `calendar.create` job (`claim(..., ids=[job])`) and processes it within `INLINE_CONFIRM_BUDGET_SECONDS` (default 3). This happens only for a ledger doctor, so no Google I/O runs on the request path. The response says `confirmed` when the job finished, otherwise `pending_sync`, and the tick finishes the job later.
- Public API (`/v1/public/clinics/{slug}`). Only clinics with `public_enabled` and a `public_slug` are visible; any other slug returns the same 404. Errors use the envelope `{"error": {"code", "message"}}` and never echo input values. Services are per doctor in the schema, so the new `services.catalog_id` groups doctor rows into one public offering (public id `COALESCE(catalog_id, id)`). A booking re-validates the slot server-side through `service.reserve`, which uses the same slot grid, horizon, lead time, exceptions and exclusion constraint as voice, and records `channel = 'web'`.
- Attach policy for form channels. A web booking always creates a new patient row, encrypted through the patients module, and never matches an existing one, because a form proves nothing about who owns a phone number. Duplicate rows for returning patients are the accepted cost. Consent purposes are recorded with source `web`. The booking needs `consent_contact: true`; otherwise it fails with `consent_required`.
- Idempotency. A client may send `Idempotency-Key`; it is stored as `web:` plus a SHA-256 of the header, and the request fingerprint includes a keyed digest of phone and name. A replay with the same contact returns the same booking, and one with a different contact returns 409 `idempotency_conflict`, so a key never reveals another person's reference. The `web:` prefix (like `bolna:`) is refused on the tools API.
- Abuse limits. Fixed windows live in `public_rate_limits`, keyed by an HMAC (PHONE_HASH_KEY) of the bucket and value, so neither IPs nor phones are stored. Over-limit requests get 429 `rate_limited`. The client IP is the address `TRUSTED_PROXY_HOPS` hops from the right of `X-Forwarded-For`, as for webhooks. Old windows are pruned during housekeeping.
- Callbacks. `callback_requests` stores name, phone and reason encrypted, with AAD `callback_request:<clinic>:<id>:<field>`. The phone hash is kept for later matching, the status starts as `open`, and retention deletes requests after `RETENTION_SESSION_DAYS`. Booking notes are encrypted on the appointment, with AAD `appointment_notes:`.
- Vercel. The repository root is the API project. `index.py` exposes `app`; pyproject `[tool.vercel] entrypoint = "index:app"` names it, and `vercel.json` sets region `dub1`, `maxDuration` 30 and excluded files. The web app is its own project under `web/`. Nothing runs at import: no migrations at cold start, and no worker-only setting is required.
- Seed. `clinic-voice seed-platform` creates the synthetic Aster Dental Studio (`aster-dental`, Asia/Kolkata), with ledger calendars, about 70 appointments across all channels, holidays and leave, and callbacks. It is idempotent, and refuses to run while any clinic without its `seed_tag` exists.

Consequences: Supabase's client roles cannot reach the data; only the backend (and service_role, which bypasses RLS) can. Function EXECUTE through PUBLIC is unchanged. The BFF must forward the client IP and the API must set `TRUSTED_PROXY_HOPS` to match, otherwise every visitor shares one rate-limit bucket. A tick without Google settings dead-letters calendar jobs for Google-mapped doctors (`calendar_unmapped`), so a deployment with any Google doctor needs those settings on the API project too.
