# ADR 0006 Patients, booking references and verified changes

Status: accepted, 29 October 2026.

T7 adds the first patient data and lets a caller change an existing booking. Caller ID is provider-asserted and phones are shared within families, so neither a phone number nor a reference alone may reveal or change a booking.

Decisions:

- Patient data. `patients` stores the name and the phone only as AES-256-GCM ciphertext under the application keyring (`TOKEN_ENCRYPTION_KEYS`). The associated data is `patient:` + clinic id + patient id + `:name` or `:phone`, so a blob copied to another row, clinic or field fails to decrypt. A keyed HMAC of the phone (`PHONE_HASH_KEY`, the same hash as `call_sessions.caller_number_hash`) supports verification. The phone is never a tool parameter: the gateway decrypts the call session's stored caller number and re-encrypts it for the patient. The tool takes an optional name, a preferred language (`en`/`hi`) and three consent flags.
- Attach policy. A booking that has a caller number and a name attaches to an existing patient only when exactly one patient with that phone hash has that name (case and whitespace folded, compared after decryption under a per-phone advisory lock). Every other booking, including any booking without a name, creates a new patient row. A phone never merges two people. The worst case of an ambiguous match is a duplicate row. With neither a number nor a name, no patient row is created.
- Consent. Each flag is tri-state. `true`/`yes` inserts a grant (at most one active grant per purpose, source `voice_call`). `false`/`no` is a decline. Empty means not asked. Any other value is refused with a speakable 422 ("please answer yes or no") before anything is written, so an unclear answer is never dropped or guessed. (A reservation replay cannot record consent later, which is why the refusal comes first.)
- Authority over an existing patient. Matching on phone plus name is not verification, so attaching to an existing patient may only add. Grants are applied. A decline revokes an active grant, and a preferred language replaces a stored one, only when the patient row was created in this transaction. Amended in the T9 re-review: a booking verified in this call session no longer gives that authority. Verification proves one booking (reference plus caller number), not who the matched patient is: a spoofed caller ID plus the patient's name attaches a new booking to that patient's record, the spoofer can verify that booking, and a later decline would then have revoked the victim's patient-wide consent and silenced all of their bookings. For a matched existing patient a decline is instead recorded as an opt-out of the new booking only (`contact_preferences` with that `appointment_id`, source `tool`, ADR 0008), and the patient's consents are untouched; when an active grant was kept the reply says so and that clinic staff change preferences for all bookings. A matched patient's language only fills a NULL. Patient-wide withdrawal of consent goes through clinic staff (staff opt-out, ADR 0008).
- Booking reference. Every appointment gets 8 Crockford base32 characters (40 bits) from `secrets`, unique per clinic, with collisions retried inside a savepoint. A database default (`new_booking_reference()`, also built on a CSPRNG) covers the backfill and raw inserts. Input normalization ignores case, spaces and hyphens and maps O to 0 and I/L to 1. The reference is spoken character by character. It is a lookup handle, not a secret by itself.
- Idempotency keys exclude patient data. The reserve key still covers only the resolved slot (ADR 0005), so no name or consent value is hashed into a key. A repeated call for the same slot in the same execution replays the first reservation, its patient and its reference, even if the name differs.
- Verification. `verify-booking` succeeds only when the reference names an appointment, in the credential's clinic, whose patient phone hash equals the session's caller-number hash. Every other case returns the same 404 and the same text: a wrong reference, a malformed one, another phone's booking, a session without a number, or another clinic. Nothing is ever looked up or listed by phone. On a shared phone, only the spoken reference is reachable. A success is stored per (session, appointment) in `call_session_verifications`, and it does not carry over to another execution, even from the same caller.
- Failure counting. Each distinct failed attempt counts once. It is keyed by an HMAC of the normalized attempt, so a provider retry is not counted twice and no reference is stored in a form that can be recovered. Counting is serialized on the session row. At 3 failures, verify, cancel and reschedule refuse with a speakable handoff message (403). This is derived from `verification_failures`; `call_sessions.status` is unchanged, so booking new slots still works on that call. A later success does not reset the count.
- Changes need verification plus read-back. Cancel and reschedule accept a booking reference that this session verified, plus `confirmed`. Only JSON `true` or the string `true` confirms. Anything else returns `changed: false` with a read-back prompt and writes nothing.
- No `cancellation_pending`. A cancel sets `cancelled` immediately and bumps `version`. It enqueues `calendar.cancel` for the old version's event in the same transaction, with the recorded event, calendar and account in the payload. The ledger is authoritative, so the slot frees at once and the calendar follows durably through the worker. A dead cancel job is visible in outbox review. The bumped version makes the old `calendar.create` superseded (it withdraws or skips) and lets future version-keyed reminders no-op.
- Reschedule. A reschedule is a new appointment for the same patient, doctor and service. It gets a new id, version 1, a new booking reference and `rescheduled_from` pointing at the old appointment. One transaction runs: action lock, doctor row lock, appointment row lock, cancel of the old appointment, slot check and insert of the new one, then enqueue of `calendar.cancel` (old) and `calendar.create` (new). Cancelling first lets the new time overlap the old hold. Any failure rolls back everything and keeps the original: slot taken, exclusion violation, outside hours or beyond the horizon. Changing the doctor or service is out of scope. The new booking is recorded as verified in the same session.
- One outcome per appointment. `appointment_changes` is unique per appointment and per idempotency key. A unique index allows one successor per appointment. With the row lock, concurrent cancel/reschedule races therefore end with exactly one change. The loser gets 409 "no longer active". Voice changes use `bolna:<execution>:<cancel-booking|reschedule-booking>:<digest>` over the appointment id (and the new UTC start), and replays return the recorded result.
- Spoken wording. "Cancelled" and "moved" are said only after the change is persisted. A new appointment is described by `service.spoken_status`, so it is "not yet confirmed" until the worker confirms it.
- Staff views. `GET /v1/admin/appointments` returns minimal fields, including the booking reference for every staff role. Owner and admin also get the decrypted name and the last two phone digits. Each appointment shown with patient details writes one audit row (`appointment.patient_details_viewed`, target the appointment id). Viewers get nulls. The full phone is never returned. Staff cancel and resolve(cancel/requeue) are audited. Requeue reuses the T4 requeue path.
- Retention. `patients.retention_until` is the latest appointment start plus `PATIENT_RETENTION_DAYS` (default 365), extended by each booking and reschedule. `clinic-voice retention purge [--dry-run]` deletes expired patients and their consents, skipping any patient with an active appointment that has not ended, and clears `appointments.patient_id`. It also deletes call sessions older than `CALL_SESSION_RETENTION_DAYS` (default 90), after clearing `appointments.call_session_id` and `appointment_changes.call_session_id`, and their verification rows cascade. Nothing schedules the purge.

Consequences: the security boundary for voice changes is still the tool credential (ADR 0005). Whoever holds it can render any `from_number`, and so can satisfy the phone factor. Over real telephony, a spoofed caller ID still needs the 40-bit reference, with 3 attempts per call. The limit is per call session only. There is no cross-session rate limit per phone hash or per clinic yet, and one should be added before a pilot. Matching names decrypts every named patient sharing a phone hash, which is acceptable for family-sized sets. Consent rows record a grant and its revocation only. A declined consent without a prior grant, and an unverified decline of an existing grant, leave no row. A session's reservation cap counts its own original reservations, whether still active or moved by a reschedule; appointments created by a reschedule do not count, so moving a booking from an earlier call costs no place. This errs conservative: a moved booking keeps its place even after its successor is cancelled. A reschedule releases the original slot in the same transaction that reserves the new one. If the new booking's calendar sync then fails, it goes to `needs_review` and the original time may already be taken. The clinic must approve the "moved ... not yet confirmed" wording with that risk in mind. Retention values are engineering defaults, not a reviewed policy.
