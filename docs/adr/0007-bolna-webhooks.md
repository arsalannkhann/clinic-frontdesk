# ADR 0007 Bolna execution webhooks and reconciliation

Status: accepted, 29 October 2026.

T8 receives Bolna's post-call status webhooks and reconciles missed ones. The Bolna documentation was rechecked on 29 October 2026 (SOURCE_REVIEW.md). It describes no webhook signature and no shared secret. It gives no API field for webhook headers: the agent schema has only `webhook_url`, and the dashboard's "Add headers" toggle has no documented format. Events carry no event id. Retries and duplicates are not described. Bolna posts once per status change, and only a 2xx counts as delivered.

Decisions:

- Authentication by path credential. Each clinic gets `tenant_credentials` rows with the new scope `webhook` (migration 013 widens the scope check). They have the same 256-bit secret, SHA-256 digest, expiry, rotation with grace, revocation and last-used tracking as tool credentials, and the prefix `cvw_`. The webhook URL is `/v1/webhooks/bolna/cvw_<id>.<secret>`. A query token was rejected: query strings are more often logged and forwarded. Header authentication was rejected because it cannot be configured through the documented API. The secret is compared with `secrets.compare_digest` against the stored digest (a dummy digest on a miss). Prefix and stored scope both keep `cvw_` and `cvt_` tokens from authenticating for each other. Every failure is the same 401 with nothing stored. The uvicorn access-log filter redacts the segment. Proxies must be configured to do the same (OPERATIONS.md).
- The tenant comes from the credential only. The payload's `agent_id` never selects a clinic. When an operator recorded `clinics.bolna_agent_id` (`clinic-voice bolna set-agent`), a payload naming a different agent is refused with 403 and nothing stored. The processor also ignores events whose agent differs from the call session's recorded agent (`agent_mismatch`).
- Defense in depth before parsing. An optional IP allowlist (`BOLNA_WEBHOOK_ALLOWED_IPS`) is checked first. X-Forwarded-For is used only with `TRUSTED_PROXY_HOPS = n`, and then the n-th address from the right is the client. The body is limited to `WEBHOOK_MAX_BODY_BYTES` (64 KiB default). A larger Content-Length is refused before reading, and a streamed body is cut off at the limit (413). Duplicate JSON keys and bodies without a UUID `id` and a well-formed status get a fixed 422.
- Minimization by allowlist. `providers.bolna.minimize_execution` keeps execution id, status, agent id, offset-aware created/initiated/updated timestamps, conversation and telephony durations, termination and hangup reasons and hangup_by (only values that look like codes), the numeric hangup provider code, call type and numeric total cost. All other fields are dropped before anything is written. The same function shapes `GET /executions` results for reconciliation.
- Inbox and dedupe. `webhook_inbox` keeps every accepted event with `received_seq` (receipt order), the minimized payload, status (`received`, `processed`, `failed`, `ignored`), an outcome code and an attempt count. The event key is `<execution id>:<status>:<sha256 of canonical minimized JSON>`, unique per clinic. Deduplicating on execution id alone, as the payload page suggests, would drop later statuses. A redelivery returns 2xx `duplicate` and writes nothing. The inbox row and its `webhook.process` outbox job commit together before the 2xx.
- Monotonic state. `call_sessions` gains `provider_status`, `provider_final`, disposition columns and reconciliation bookkeeping. Ranks run scheduled/rescheduled < queued < initiated < ringing < in-progress < call-disconnected < final. A status of lower rank is `stale`. Once a final status (completed, balance-low, busy, no-answer, canceled, failed, stopped, error) is applied, any other status is `stale`. A repeat of the same final status only fills disposition fields that are still empty. Equal ranks are lateral moves. `call-disconnected` or a final status sets the session `ended` (the gateway then refuses tools for it). Which statuses are final is our reading of the docs, since they name only `completed`.
- Unknown executions are ignored, not created. A session exists only once the trusted gateway saw the call (tool or context call), so an event for any other execution is kept as `ignored`/`unknown_execution`. Creating sessions from webhooks would let a leaked webhook URL fabricate call records. The cost: calls that never reached a tool leave no session (their events remain in the inbox).
- Processing. `webhook.process` counts the attempt, then locks the inbox row, the call session row (FOR NO KEY UPDATE) and its own fenced outbox row in that order. It commits the session update, the inbox outcome and the job completion together. A lost lease rolls everything back. An event that is no longer `received` completes the job unchanged, so a retried or duplicated job is idempotent. A dead job marks its event `failed` (SKIP LOCKED, so the dead-letter path never waits on a processor). Staff requeue returns the event to `received`.
- Reconciliation. Worker housekeeping enqueues `bolna.reconcile` jobs, but only when the worker has a Bolna port (`--bolna fake|live`; fake refused outside `_test`/`_dev` databases like the fake calendar). It picks at most `BOLNA_RECONCILE_BATCH` unfinished sessions whose start and last provider update are both older than `BOLNA_RECONCILE_AFTER_MINUTES`. Each session gets at most 6 polls, with the delay doubling up to 24 h, and session rows are taken with SKIP LOCKED. The job reads `GET /executions/{id}` with the connection idle and applies the same monotonic rule. Provider errors follow the outbox rules: a timeout or retryable error retries with backoff and changes nothing (a read is safe to repeat), an unknown execution completes, and a mismatched execution id dead-letters.
- T7 review fold-in. `admin.requeue_outbox` reads the job status unlocked and returns 409 before taking any lock unless the job is dead, then locks and re-checks as before. A job being dead-lettered still reads `processing` until that transaction commits. Dead-lettering locks the outbox row before its `on_dead` hook updates the appointment, so requeue no longer waits on that row while holding the appointment (regression test). `locks.py` now states the worker's real orders.

Consequences: a leaked webhook URL lets its holder mark that clinic's known call sessions ended or final, and fill disposition codes. It cannot read data, select another clinic or create sessions. Rotation follows the tool credential procedure, plus updating `webhook_url`. Path credentials appear wherever full paths are logged outside this application. The status ranks and the final set are inferred, not documented. If Bolna can move a call out of a status we treat as final, that update is ignored (visible as `stale` in the inbox). Lateral moves between equal ranks (scheduled/rescheduled) follow processing order, which may differ from receipt order under concurrent workers. A residual deadlock remains, outside requeue: claim()'s lease_expired dead-letter can meet a stale worker's confirm in reverse order (PostgreSQL aborts one, and both are retried). The compiler does not yet emit `webhook_url`, and no live delivery or execution read has been performed.
