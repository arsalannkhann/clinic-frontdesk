# Development and operations

## Local lifecycle

Follow README setup. `docker compose stop` preserves data; `docker compose down` also preserves the named volume. `docker compose down -v` deletes local data and must only be used intentionally. Migrations run as a separate CLI step before API start, from the repository root. The application never auto-creates tables. The schema lock serializes migration processes, and checksums reject edits to applied files.

The image runs as UID 10001. Build with `docker build -t clinic-voice:dev .`; pass DATABASE_URL through your environment/secret manager. Issue tool credentials with the CLI after migrating; the plaintext token is printed once and must go straight to the gateway's secret store. Inside a Compose network the DB hostname is `db:5432`, not localhost:55432. The Dockerfile does not run migrations on startup. No deployment automation is configured.

Readiness checks schema availability and reports integrations `not_configured`. It does not certify calendar sync or a working phone line. Keep liveness separate so a provider outage does not trigger a restart loop. Outbox entries are consumed only while a worker runs (see below).

## Running the worker

`clinic-voice worker --calendar fake` runs the outbox worker in a loop: it claims up to 10 due jobs, processes them, and polls again after `--interval` seconds (default 2, 0.1-300) when idle, reusing one database connection across polls. `--once` processes one batch and exits; `--worker-id` names the lease owner (default `host:pid`, at most 128 characters; use a distinct id per process). SIGINT/SIGTERM let the current job finish and release the batch's unstarted jobs back to pending (due immediately; `max_attempts` grows by one so the unused claim costs nothing). Database errors close the connection, are logged by type, and back off 1, 2, 4 ... up to 30 seconds before reconnecting. `--calendar fake` uses an in-process FakeCalendar and prints a warning: nothing reaches a real calendar, and events vanish when the process exits. It is refused unless the database name ends in `_test` or `_dev` or `APP_ENV=development` is set (`app_env` defaults to `production`). Without `--calendar` the worker refuses to start. `--calendar google` uses the Google Calendar adapter with each doctor's calendar account (or the clinic's only active account when the doctor has none) and refuses to start unless `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` and a valid `TOKEN_ENCRYPTION_KEYS` are set. Its adapter timeout is 10 seconds. Every real adapter must declare `timeout_seconds` of at most a quarter of the 2-minute lease (`check_ports` refuses to start otherwise; only FakeCalendar is exempt). A create job keeps targeting the calendar it first wrote to after a doctor's booking calendar is remapped; new bookings use the new calendar. Run as many workers as needed; `SKIP LOCKED` keeps claims disjoint and fenced completion makes a reclaimed job safe. A worker killed mid-job leaves its job `processing` until the lease expires; another worker then reclaims it and recovers by reading the deterministic event id, unless the job already used all attempts, in which case it is dead-lettered `lease_expired`. `httpx`/`httpcore` logging is set to WARNING in the worker.

`--bolna fake|live` (optional) adds the Bolna port for call reconciliation. Without it the worker enqueues no reconciliation and does not claim `bolna.reconcile` jobs (they wait for a worker with a Bolna port). Only clinics with a configured agent id (`clinic-voice bolna set-agent`) are reconciled. `--bolna fake` is refused like `--calendar fake` (FakeBolna knows no executions, so reconcile jobs complete without change). `--bolna live` reads `GET /executions/{id}` with `BOLNA_API_KEY` (refused when unset; 10 s timeout); running it against a real account is an owner decision (AGENTS.md) and has not been done. When idle, housekeeping (at most every 10 minutes) enqueues `bolna.reconcile` for at most `BOLNA_RECONCILE_BATCH` (default 50) call sessions without a final provider status whose start and last provider update are older than `BOLNA_RECONCILE_AFTER_MINUTES` (default 30). Each session is polled at most 6 times, the delay doubling after each poll (30 min, 1 h, 2 h ... capped at 24 h). Sessions still unfinished after that keep `provider_final = false` with `reconcile_count = 6`; review them with `SELECT clinic_id, id, provider_status, started_at FROM call_sessions WHERE NOT provider_final AND reconcile_count >= 6`.

## Google Calendar setup (requires owner action; not performed)

None of these steps has been performed for this repository: no Google Cloud project, OAuth client or calendar exists, and no live Google call has been made. An owner who wants to validate against a real test account does the following with a non-production Google account:

1. In Google Cloud console create a project, enable the Google Calendar API, and configure the OAuth consent screen (External/testing is fine; add the test Google account as a test user). Add the scopes `https://www.googleapis.com/auth/calendar.events` and `https://www.googleapis.com/auth/calendar.freebusy`.
2. Create an OAuth client of type "Web application" with the authorized redirect URI `http://localhost:8000/v1/oauth/google/callback` for local runs (Google allows plain http only for loopback) or the deployment's `https://.../v1/oauth/google/callback`. It must match `GOOGLE_REDIRECT_URI` exactly.
3. Generate the token keyring: `clinic-voice generate-key` prints a key; set `TOKEN_ENCRYPTION_KEYS=k1:<key>` (key ids: 1-32 letters, digits, `_` or `-`). Store the client secret and keys in a secret manager or an untracked `.env`, never in Git. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`.
4. In the test account create a dedicated booking calendar; note its calendar id. As an owner/admin staff user call `POST /v1/admin/calendar/google/start`, open the returned URL in a browser, consent with the test account, and confirm the callback page says the calendar is connected (`GET /v1/admin/calendar/accounts`).
5. Map a synthetic doctor: `PATCH /v1/admin/doctors/{id}` with `booking_calendar_id`, `busy_calendar_ids` and, if the clinic has several accounts, `calendar_account_id`. Run `clinic-voice worker --calendar google --once` after a synthetic reservation and compare the database, the calendar event and `appointment-status`.

Without these settings the calendar endpoints return 503 "Calendar integration not configured". Key rotation: prepend a new key (`TOKEN_ENCRYPTION_KEYS=k2:<new>,k1:<old>`); new ciphertext uses `k2` and old rows still decrypt with `k1`. Do not remove a key while rows reference it (`SELECT key_id, count(*) FROM calendar_accounts WHERE status <> 'revoked' GROUP BY 1`); there is no re-encryption command yet, so reconnecting the account is the way to move it to the new key. A row whose key is missing makes its jobs dead-letter with `provider_permanent`. Disconnect with `DELETE /v1/admin/calendar/google/{id}`; doctors keep the id and their jobs become `calendar_unmapped` until remapped. Cancels of events written by a disconnected account also dead-letter `calendar_unmapped`: remove those events by hand in the calendar. The Google revocation runs as a `calendar.revoke_grant` outbox job in the `--calendar google` worker (a fake worker dead-letters it `no_revoker`; requeue it once a Google worker runs). If it dead-letters after its retries, the stored token is kept: the owner removes the app's access in the Google account (in the Google Account security settings, under third-party apps with account access; the exact menu path is not verified here) and then requeues the job, which treats Google's `invalid_token` answer as revoked and clears the ciphertext. An account in status `error` means Google rejected its refresh token (user removed access, password reset, or the testing-mode token expired); reconnect with `POST /v1/admin/calendar/google/start?replace=true`. Connecting a second account requires `replace=true`, which retires the old account locally (token forgotten, audit `calendar.account_replaced`) but does not revoke it at Google: Google's revocation is grant-wide, so it would also disable the new account if the same Google user reconnected. If a different Google user was connected before, the owner should remove that stale grant in that user's Google account at https://myaccount.google.com/permissions. A rejected callback (missing refresh token or scopes) is also discarded without a Google revoke; remove the grant there if wanted. An explicit DELETE revokes at Google and therefore also disables any other calendar account connected with the same Google user (those turn `error`). Outstanding cancels whose writing account was revoked or replaced use the doctor's current account. Reconnecting after a disconnect cancels that disconnect's pending Google revocation (job done with `revoke_superseded`) and forgets the old token locally, because it may be the same Google user; if it was a different user, remove the old grant at https://myaccount.google.com/permissions. Known limitation: a disconnect also disconnects the same Google user in other clinics, since accounts are not tied to a Google identity yet (a keyed hash of the Google `sub` via the `openid` scope is a follow-up that needs owner approval). Expired OAuth states are pruned by the worker when idle. uvicorn access-log lines have their query strings stripped (the callback query carries the authorization code); do not enable other request logging that records query strings.

## Bolna gateway setup (requires owner action; not performed)

No Bolna account, agent, number or call has been used by this repository. The gateway routes run in the API process and need `TOKEN_ENCRYPTION_KEYS` and `PHONE_HASH_KEY` (`clinic-voice generate-key` for each; the hash key is a bare base64 key, not `kid:key`). Never rotate `PHONE_HASH_KEY` casually: existing `caller_number_hash` values stop matching. To review the agent payload: set `BOLNA_GATEWAY_BASE_URL` (the public https base URL Bolna will reach) or pass `--gateway-url`, then run `clinic-voice bolna compile-agent --clinic <uuid>`; the output has `Bearer <redacted>` where the gateway credential goes and `webhook_url` ending in `/v1/webhooks/bolna/<redacted>` where the webhook credential goes (provisioning fills both; a hand-configured agent needs its own, see the webhook setup below). For an agent configured by hand, issue that credential with `clinic-voice credential issue --clinic <uuid> --label bolna-agent --scope bolna` (`cvb_...`): it works on `/v1/bolna/*` only and is refused by `/v1/tools/*`. Hand-configured agents still holding a `tools` (`cvt_`) token keep working on the gateway; rotate them to a `bolna` token when convenient. Creating the agent at Bolna, inserting a real token, assigning a number and test calls need explicit owner authorization; the provisioning flow (T10, below) automates the first three. `BOLNA_API_KEY` and `BOLNA_API_BASE` are read only by `clinic-voice worker --bolna live` (execution reads for reconciliation, reminder calls, provisioning). Leave the key unset until the owner authorizes live use. Before enabling, re-run the contract checks in docs/SOURCE_REVIEW.md against a test agent: tool request body shape, `execution_id`/`from_number` substitution, multilingual switching and the Sarvam voice id.

Unsubstituted call context: a warning `call context unsubstituted clinic=<id> tool=<tool> fields=<names>` (logger `clinic_voice.bolna`) means a Bolna tool request arrived with `execution_id`, `from_number` or `agent_id` still a literal template (`{from_number}`, `%(agent_id)s` or another `%(...)` specifier, `<agent_id>`, or the variable name). The gateway refused it with 422 `context_unsubstituted` and wrote nothing; the agent was told to offer a handoff to clinic staff, so no booking tool works on that line until it is fixed. Either the agent's tool `param` templates or prompt variables are misconfigured (recompile with `clinic-voice bolna compile-agent` and compare with what is configured at Bolna; the prompt must define the variables for Bolna to auto-substitute them), or Bolna does not substitute these variables at all, in which case live booking stays blocked until SOURCE_REVIEW.md's open question is resolved. The log line carries no values; there is no counter or metric, so count the log lines per clinic. An empty `from_number` is not refused (withheld number).

Missing execution id: a warning `call context missing clinic=<id> tool=<tool> fields=execution_id` means a tool request arrived with `execution_id` absent, `null` or blank. The gateway refused it with 422 `context_missing` (same handoff sentence) and wrote nothing. The agent's tool `param` templates do not send the execution id, or Bolna rendered it empty; fix as for an unsubstituted context. An `execution_id` that is present but not a UUID (`None`, `null`) gets the generic validation 422 and no log line from the gateway.

Incomplete call context: `call context incomplete clinic=<id> tool=<tool> empty=<names> malformed=<names>` (logger `clinic_voice.bolna`, `-` for none) is logged for an accepted request whose `from_number` or `agent_id` is unusable; nothing is refused and the value is ignored as before. `empty` (info level) means blank: a withheld caller number, or an agent whose tools do not send `agent_id`. `malformed` (warning level) means present but not E.164 (`from_number`: `None`, `null`, `unknown`, `anonymous`) or not a UUID (`agent_id`). On the first live call, `malformed=from_number` on every call means Bolna renders the caller number in an unexpected form and caller-number verification cannot work; `empty=from_number` on every call (when callers do not withhold) suggests the variable is not wired into the tool params. The line carries field names and categories only, never values.

## Bolna webhook setup (requires owner action; not performed)

No Bolna delivery has reached this code. To prepare one:

1. Provisioned clinics (migration 017 onward): nothing to do. The agent step issues a `webhook`-scope credential (label `provisioning:webhook`) with the tool credential and sends `<BOLNA_GATEWAY_BASE_URL>/v1/webhooks/bolna/<cvw_ token>` as the agent's `webhook_url`; every agent rewrite (reset after review) issues a new one and revokes the old. Verified against FakeBolna and MockTransport only, not against a live agent. Do not edit the webhook URL of a provisioned agent in the dashboard: verify reports `webhook_mismatch` when Bolna's agent read shows a different URL (and cannot check when the read omits it, which is undocumented).
   Hand-configured agents (and clinics provisioned before migration 017, whose `webhook_credential_id` is NULL until their agent step runs again): `clinic-voice credential issue --clinic <uuid> --label bolna-webhook --scope webhook` prints `token=cvw_...` and `webhook_path=/v1/webhooks/bolna/cvw_...` once. The webhook URL is `<public https base>/v1/webhooks/bolna/<token>`; treat the whole URL as a secret. Set it as the agent's `webhook_url` in the dashboard. Provisioning never touches credentials of other labels. When a clinic provisioned before migration 017 re-runs its agent step (reset after a review), provisioning replaces that hand-set `webhook_url` with a managed one but leaves the hand-issued credential active and unused: find it with `clinic-voice credential list --clinic <uuid>` (label `bolna-webhook`, `last_used_at` no longer advancing) and revoke it with `clinic-voice credential revoke <credential-id>`. Bolna documents no signing or API-settable headers, so do not rely on the dashboard's "Add headers" toggle.
2. `clinic-voice bolna set-agent --clinic <uuid> --agent-id <bolna agent uuid>` records the agent id; deliveries naming another agent, or none, are then refused (403). `--clear` removes it. Reconciliation runs only for clinics with an agent id.
3. Optional: `BOLNA_WEBHOOK_ALLOWED_IPS=13.203.39.153,13.126.9.249,13.202.133.53` (recheck the addresses on Bolna's webhook page first). Behind a reverse proxy set `TRUSTED_PROXY_HOPS` to the number of proxies that append to X-Forwarded-For; otherwise the proxy's own address is checked and every delivery is refused. With `TRUSTED_PROXY_HOPS` > 0 the application must not be directly reachable (bind it to the proxy network only): a direct client could write any X-Forwarded-For value. Until request rate limiting exists, intake of events for unknown executions is unbounded: each distinct event with a valid webhook credential is stored (`ignored`/`unknown_execution`), so watch `webhook_inbox` growth per clinic and rotate a credential that is being abused. `WEBHOOK_MAX_BODY_BYTES` (default 65536) caps the body.
4. Configure the proxy/load balancer not to log paths under `/v1/webhooks/` (or redact the last segment); the application's own access log already redacts it.
5. Run a worker so `webhook.process` jobs are applied. Rotation of a hand-issued webhook credential works as for tool credentials (`credential rotate`, update `webhook_url`, watch `last_used_at`, revoke); for a provisioned clinic, reset and re-run the agent step instead. Inspect deliveries with `SELECT received_seq, execution_id, provider_status, status, outcome FROM webhook_inbox WHERE clinic_id=... ORDER BY received_seq`: `ignored` + `unknown_execution` means the call never reached the tool gateway; `stale` means an out-of-order or post-final status; `agent_mismatch` means the session's agent differs. A dead `webhook.process` job marks its event `failed`; requeue it after fixing the cause and the event is processed again.

## Confirmations and reminders (requires owner authorization; not performed)

Patient messaging and outbound calls need the owner's explicit authorization. Until then leave `outbound_enabled` false (the default) for every clinic. No live messaging provider exists. Choosing one, re-reading its documentation into SOURCE_REVIEW.md and writing a contract-tested `MessagingPort` adapter is an owner action, and so is the reminder-call wording of the Bolna agent. Local development: `clinic-voice worker --calendar fake --bolna fake --messaging fake` (refused outside `_test`/`_dev` databases unless `APP_ENV=development`); enable `outbound_enabled` for a synthetic clinic through `PATCH /v1/admin/clinic`. With `--bolna live`, an enabled clinic with an outbound agent gets real reminder calls through `POST /call`.

Release blocker (owner review required before any clinic enables outbound calls): reminder calls use a separate Bolna agent, recorded with `clinic-voice bolna set-agent --clinic <id> --outbound --agent-id <uuid>` (`--clear` removes it; the inbound agent is refused). Its prompt, wording and configuration have not been designed; the owner must review them and confirm in the Bolna dashboard that the outbound agent has no tools (no booking, verification, change or opt-out). The gateway refuses those tools on reminder-call executions as defense in depth, not as the control. Webhooks from the outbound agent are accepted and ignored (no call session), so reminder-call statuses are not recorded.

Messaging provider acceptance criteria (before an adapter may declare them True): `idempotent_reference` (the provider deduplicates by our reference for at least 12 hours) and `consistent_lookup` (lookup by reference is read-after-write consistent), each proven from official documentation in SOURCE_REVIEW.md and contract fixtures. Without both, a message whose outcome is unknown and whose lookup finds nothing goes to `needs_review` instead of being resent.

- Review `GET /v1/admin/reminders?status=needs_review`. These contacts timed out with an unknown outcome and are never retried automatically. For a call, look up the `provider_execution_id` (if any) or the `contact_reference` in `user_data` in the Bolna dashboard. Nothing marks such a row resolved yet; it stays for the record.
- `suppressed` with `budget_exhausted` means the daily budget left no room before the appointment. Raise `daily_contact_budget` if that is expected volume.
- Dead `notification.send`/`reminder.call` jobs have already moved their row to `failed` or `needs_review` (or housekeeping does, `job_lost`, within minutes). They cannot be requeued (409, since T12), nor can a dead `reminder.stop`: a timed-out attempt may already have reached the patient, so review the contact instead. A dead `reminder.stop` moves its unstopped calls to `needs_review` (`stop_failed`): stop them in the Bolna dashboard if they are still queued.
- Turning `outbound_enabled` off suppresses every contact that comes due while it is off, permanently; turning it back on does not resend them. A `daily_contact_budget` of 0 also disables outbound contact.
- Patient-wide opt-outs and consent withdrawals are staff only; the voice tool, and a decline at reserve-slot for an existing patient, opt out one booking (carried over on a voice reschedule). Consent granted later is not backfilled for an already-planned appointment version. `POST /v1/admin/appointments/{id}/opt-out/remove` undoes an opt-out when the patient asks the clinic; contacts already suppressed stay suppressed.
- Retention purge also deletes the purged patients' opt-outs. Their planned contacts stay (no patient data) and are suppressed (`no_patient`) if they come due.

## Retention purge (operator-run; not scheduled)

`clinic-voice retention purge --dry-run` prints how many patients, consents, appointment links and call sessions a purge would remove, then rolls back; without `--dry-run` it deletes them in one transaction. Patients whose `retention_until` (latest appointment start + `PATIENT_RETENTION_DAYS`, default 365) has passed are deleted with their consents unless they still hold an active appointment that has not ended; their appointments stay with `patient_id` cleared. Webhook inbox events received more than `CALL_SESSION_RETENTION_DAYS` ago are deleted (`webhook_events`). Call sessions older than `CALL_SESSION_RETENTION_DAYS` (default 90) are deleted with their verification records after `appointments.call_session_id` and `appointment_changes.call_session_id` are cleared. Output is counts only. Nothing runs it automatically; schedule it only after the owner approves a retention policy. Back up first: deletion is permanent.

Reschedules release the original slot before the new booking's calendar sync completes. Watch `needs_review` appointments with a `rescheduled_from` and call those patients; the clinic must approve that spoken wording (ADR 0006) before pilot traffic.

Migration 013 was likewise revised before release (security review): a database that applied the earlier branch-only 013 fails the checksum check and must be recreated. Migration 012 was revised before release (backfill and indexes). Databases that applied the earlier branch-only version of `012_patients.sql` fail the checksum check: recreate them (`docker compose down -v` for local data, or drop the `_test` database's schema). Released databases are unaffected (012 has never been on `main`).

Staff can review appointments at `GET /v1/admin/appointments` and settle `needs_review` ones with `POST /v1/admin/appointments/{id}/resolve` (`requeue` after fixing the cause, or `cancel`). Callers who hit the verification handoff (3 failed booking references in one call) must be helped by staff.

## Clinic provisioning (requires owner authorization for live use; not performed)

Run only against fakes so far. With `--bolna live`, advancing provisioning creates or updates an agent on the real Bolna account and routes a real number, so it needs the owner's explicit authorization first. Prerequisites: `BOLNA_GATEWAY_BASE_URL` on the worker (else the agent step fails `gateway_unconfigured`), a connected calendar with a mapped doctor, and an existing number on the Bolna account (buy or port it outside this system; nothing here purchases numbers). Steps as the owner: `POST /v1/admin/provisioning/advance` (calendar), advance (agent), `POST /v1/admin/provisioning/number {phone_number_id}` (from the Bolna dashboard or `GET /phone-numbers/all`), advance (number), advance (verify), then set and approve the emergency and handoff scripts (`PATCH /v1/admin/clinic`) and `POST /v1/admin/provisioning/activate`. Read progress with `GET /v1/admin/provisioning`. The Bolna gateway answers only once the clinic is `verified` (context and read-only tools) and accepts bookings, cancellations, reschedules and opt-outs only once it is `active`; to place owner test calls in `verified`, the owner sets `PATCH /v1/admin/clinic {"test_calls_enabled": true}` (audited) and turns it off again after testing. Callers of a line that is not open hear "this line isn't accepting bookings yet". Activation does not enable reminders: `outbound_enabled` stays as it was, and the tool-free reminder agent is still set by hand (`bolna set-agent --outbound`).

Review (`manual_review`): `create_uncertain`, `lease_lost` or `lookup_unavailable` means an agent create's outcome is unknown and the listing could not prove it absent. In the Bolna dashboard look for agents named `clinic-<clinic id hex>-v1`: delete duplicates and keep at most one. If one remains, a plain reset lets the next agent step find it by name and update it. If none exists, reset with `{"confirm_no_stray_agent": true}` (only accepted after `create_uncertain` or `lease_lost`): a plain reset keeps the create intent, and the next step would refuse again. `agent_conflict`: the agent found or created belongs to another clinic (or is this clinic's outbound agent), or `bolna_agent_id` changed while the step ran; nothing was written to that agent before the check, and a credential the conflicting write delivered is revoked. Find out which clinic owns it before resetting. `credential_inactive`: the agent's tool credential or webhook credential was revoked or expired; reset re-runs the agent step with fresh ones. `webhook_mismatch`: Bolna's agent read shows a `webhook_url` that is not `<BOLNA_GATEWAY_BASE_URL>/v1/webhooks/bolna/` with the recorded webhook credential and its exact secret (edited in the dashboard, mangled, or a stale agent version); reset re-runs the agent step, which rewrites it. `agent_ambiguous`: two agents carry the name; delete one, then reset. `agent_preconfigured`: the clinic already has a hand-set `bolna_agent_id`; clear it (`bolna set-agent --clinic <id> --clear`) if provisioning should own the agent, then reset. `tools_mismatch`, `agent_mismatch`, `credential_mismatch` and `webhook_mismatch` reset to the agent step, which rewrites the agent; `number_mismatch` resets to the number step. `retries_exhausted`: the provider kept failing; check the API key and Bolna status, then reset. `failed` codes (`unauthorized`, `provider_permanent`, `gateway_unconfigured`, `agent_config_invalid`, `prompt_unavailable` when `agents/prompts/receptionist.md` is missing from the deployment) need the configuration fixed before a reset. Reset returns to `resume_state` and clears the step attempt counters. Dead `provision.step` jobs cannot be requeued through the outbox route; use reset and advance.

Clinics set up by hand before T10 (agent recorded with `clinic-voice bolna set-agent`, number routed in the Bolna dashboard) have no provisioning row, so the gateway refuses their calls from the moment migration 015 is applied. They stay dark until an owner sets and approves the emergency and handoff scripts (new columns, so this cannot be done before the migration) and an operator runs `clinic-voice provisioning activate-manual --clinic <uuid>`. Schedule the upgrade per clinic in a quiet window and have the owner ready. The command requires `bolna_agent_id` (not used by another clinic), approved scripts and a ready calendar; it accepts no row or an untouched draft row and refuses any other provisioning state; it records state `active` with a `manual_activation` event (no actor). It does not verify anything at Bolna (agent, tool URLs, credential or number routing): check those in the dashboard first. Owner provisioning routes on such a clinic return 409 "Manual setup: use clinic-voice provisioning activate-manual" and create nothing. A concurrent change gives a clean error; re-run after checking the state.

Test calls: while `test_calls_enabled` is on in `verified`, the line is fully open to anyone who dials the number, not only the owner. Real callers can then book, cancel, reschedule and opt out, and those bookings are real. Route the number only when ready, keep the test window short and turn test calls off (`PATCH /v1/admin/clinic {"test_calls_enabled": false}`) immediately after; a booking write in flight when it is turned off is refused.

Retention and offboarding: `provisioning_events` is append-only (a trigger rejects UPDATE and DELETE) and `provisioning` rows reference the clinic, so neither is removed by the retention purge. The events hold no patient data (states, step, outcome codes, staff ids). A retention and clinic-offboarding policy is still needed before production (how long events are kept, and how a departing clinic's rows are removed by a privileged migration-role procedure that disables the trigger); it is not implemented.

Development databases: migrations 012 to 015 were edited before release (015 after commit c3bbe2b). Any database that applied an earlier version of one of them fails the checksum check at startup; rebuild it (drop and recreate the schema or the `_dev`/`_test` database, then migrate). None of them has been released, so no production database is affected. Migration 016 (T12) adds the `bolna` scope, `appointments.tool_credential_id` and `clinics.include_reference_in_messages`; provisioning credentials issued before it stay `tools` scope, so a rebuilt database is the simplest way to get `bolna` tokens everywhere.

Credential note: each agent attempt issues a new `bolna`-scope credential (`provisioning:agent`, `cvb_`; before migration 016 these were `tools` scope), accepted by `/v1/bolna/*` only, and (migration 017) a new `webhook`-scope credential (`provisioning:webhook`, `cvw_`) for the agent's `webhook_url`. After a successful agent write the clinic's other credentials of both labels are revoked; when a step ends in failed or manual_review, all of them are revoked except the two the agent holds and the two a timed-out write may have delivered. `clinic-voice credential list --clinic <id>` shows them. Verify outcomes: `ok`; `token_unchecked` (Bolna masked the `api_token`); `webhook_unchecked` (the agent read has no `webhook_url`, which `GET /v2/agent` does not document, or the row predates migration 017 and its webhook URL is not managed); `token_and_webhook_unchecked` (both). An unchecked webhook means status webhooks are not proven: confirm the URL in the dashboard and watch `webhook_inbox` after the first test call.

## Dead-letter review

Jobs dead-letter after `max_attempts` (8) failures or on an outcome retrying cannot fix: `external_conflict` (the doctor's busy calendar overlaps the hold), `calendar_unmapped` (doctor has no booking calendar), `event_mismatch` (an event with the deterministic id exists with other times or is cancelled), `appointment_past` (the appointment started before it could be projected), `lease_expired` (workers kept dying on it), `provider_permanent`, `unknown_kind` (a kind with no handler yet), `bolna_unconfigured` (a reconcile job run directly without a Bolna port; the worker loop does not claim them), `execution_mismatch` (Bolna returned another execution's id), `bad_payload`. A dead calendar.create moves a still-pending appointment to `needs_review`; the caller is told staff will follow up. Owners and admins list them with `GET /v1/admin/outbox?status=dead`. Resolve the cause first (map the calendar, clear the conflicting external event, or contact the patient), then `POST /v1/admin/outbox/{id}/requeue`: it keeps `attempts`, grants 8 more (`max_attempts = attempts + 8`), and for a calendar.create whose `last_error` is a calendar failure code returns the appointment to `pending_sync`; the worker re-checks everything before writing. Requeue is refused (409) once the appointment has started, and at once for a job that is not dead (including one being dead-lettered at that moment). Do not requeue `external_conflict` without resolving the conflict; it will dead-letter again. Monitor `pending` age and `processing` jobs whose lease keeps expiring.

## Credential rotation

1. `clinic-voice credential rotate <old-id> --grace-minutes 60` prints the replacement token; the old credential now expires within the grace window (rotation never extends an existing expiry).
2. Deploy the new token to the caller: recompile the Bolna agent with it and update the agent. Provisioning cannot rotate the credential of an active agent yet (follow-up); an owner does it by hand.
3. Confirm `last_used_at` on the old credential stops advancing (`credential list --clinic <uuid>`; resolution is about five minutes), then `clinic-voice credential revoke <old-id>`.

For a suspected leak, revoke first; revocation is effective on the next request. Migration 002 drops nothing; `TOOL_TOKEN`/`CLINIC_ID` environment variables are now ignored and should be deleted from deployed environments.

## Staff bootstrap and recovery

Create a clinic's first owner with `clinic-voice staff create-owner --clinic <uuid> --email <address>`; the password is read from a hidden prompt or a single stdin line, never from arguments. The owner then creates other staff via `POST /v1/staff/users`. To recover a locked-out or forgotten account run `clinic-voice staff set-password --email <address>`: it clears the lockout, revokes every session for that user and writes a `staff.password_reset` audit event. Migration 003 only adds tables.

## Failure handling to implement

Calendar uncertain (implemented in the worker): keep pending/review state, reconcile using stable event ID; never blindly reinsert or announce success. Messaging failure: preserve appointment, retry delivery independently and alert after bounded attempts. Webhook gap (implemented, T8): reconciliation polls executions of unfinished sessions with backoff. Reminder race: version-check before dialing and reconcile provider cancellation. Database failure: fail closed with a retryable safe response.

Proposed metrics: booking outcome counts, tool latency, pending reservation age, outbox age/retries/dead letters, calendar conflicts, webhook gaps, transfer failures, language task success and provider spend. Use opaque correlation IDs; no patient identifiers as metric labels.

Rollback app versions only if compatible with schema. No automatic down migrations are provided. Restore from backups only under a reviewed recovery plan; keep the reservation ledger and external calendar reconciled.

## Staff dashboard (T11)

Development: run the API on port 8000, then `cd dashboard && npm ci && npm run dev` and open http://127.0.0.1:5173. With `VITE_API_BASE_URL` empty the Vite dev server proxies `/v1` to `DASHBOARD_API_PROXY_TARGET` (default `http://127.0.0.1:8000`), so no CORS is needed. Sign in with a staff user created by `clinic-voice staff create-owner`.

Production build: `cd dashboard && npm ci && VITE_API_BASE_URL=<API origin or empty> npm run build`, then serve `dashboard/dist/` as static files. Two layouts:

- Same origin (preferred): one host serves `dist/` and forwards `/v1/` to the API. Build with `VITE_API_BASE_URL` empty and leave `DASHBOARD_ORIGINS` unset.
- Separate origins: the API must see the staff/admin paths unprefixed (`/v1/...`); behind a path prefix CORS is not sent (fails closed). Build with `VITE_API_BASE_URL=https://api.clinic.example` and start the API with `DASHBOARD_ORIGINS=https://dash.clinic.example` (comma-separated for several; exact origins, no wildcards). A malformed value fails startup.

Serve `dist/` over TLS with the headers listed in docs/SECURITY.md (CSP with `frame-ancestors 'none'`, HSTS, nosniff, no-referrer). Users must sign in again after a reload; that is intended (the token is never stored). The Appointments and Schedule exceptions screens show and accept times in the clinic's time zone (named next to each time input) and do not open if the zone cannot be loaded. For the calendar connection, Google's consent page opens in a new tab; after consenting, close it and refresh the Calendar screen.

Development database: the fake worker ports (`--calendar/--bolna/--messaging fake`) run only against a database whose name ends in `_test` or `_dev` (or with `APP_ENV=development`). `.env.example` points at `clinic_voice_dev`; create it once with `docker compose exec db createdb -U clinic clinic_voice_dev`, keep `clinic_voice_test` for pytest (the suite truncates it).

## Supabase, Vercel and the worker tick (P1, ADR 0010; not deployed)

None of this has been run against Supabase or Vercel; the steps below need the owner's accounts and authorization.

- Migrations: run `clinic-voice migrate` over a direct (5432) or session-pooler connection, never the transaction pooler (6543). The API itself may use the transaction pooler; `connect` detects port 6543, or set `DATABASE_POOLER=transaction|session|none` in the process environment to override. Migration 018 enables RLS on every table and, where the Supabase roles exist, revokes `anon`/`authenticated` privileges; the backend's owner role is unaffected. New tables in later migrations must enable RLS (a test enforces it).
- Vercel API project: repository root. `index.py` exposes the app (pyproject `[tool.vercel] entrypoint = "index:app"`), `vercel.json` pins region `dub1` and `maxDuration` 30, `.vercelignore` keeps web, tests, docs and migrations out of the bundle but ships `agents/prompts/*.md` (provisioning compiles the agent prompt from them; a missing prompt fails the step as `prompt_unavailable`). Nothing migrates at cold start. Set `DATABASE_URL` (pooler), `TOKEN_ENCRYPTION_KEYS`, `PHONE_HASH_KEY`, `WORKER_TICK_SECRET`, `PUBLIC_PROXY_SECRET` (the same value in the web BFF, which sends it as `X-Proxy-Secret` together with the visitor address in a single `X-Client-IP` header on every `/v1/public/*` and `/v1/chat/*` call; without it those paths fall back to `TRUSTED_PROXY_HOPS` and `X-Forwarded-For`, which is for development only) and, if any doctor uses Google, the Google settings (otherwise the tick dead-letters those doctors' jobs as `calendar_unmapped`).
- Tick: generate `WORKER_TICK_SECRET` (≥32 random characters) into the secret store, then schedule pg_cron + pg_net to `POST /v1/internal/worker/tick` with `Authorization: Bearer <secret>` every minute. Call `net.http_post` with `timeout_milliseconds := 25000`: pg_net's default timeout (5 s) is shorter than the tick's budget, so with the default every tick that has work would be recorded as a timeout (the tick still runs, but its result is lost). The route is 404 while the secret is unset. `WORKER_TICK_BUDGET_SECONDS` (default 8) must stay below the function's `maxDuration`. The response holds only `{claimed, housekeeping}`; a non-200 or repeated `housekeeping: failed` needs a look at the logs.
- Ledger calendars: set a doctor's `booking_calendar_id` to `ledger:<doctor id>` to run without Google. `clinic-voice worker --calendar ledger` is the long-running equivalent of the tick and is allowed in production. Public bookings for ledger doctors confirm inline within `INLINE_CONFIRM_BUDGET_SECONDS` (default 3, 0 disables).
- Public site: a clinic appears at `/v1/public/clinics/{slug}` only after setting `public_slug` and `public_enabled` (and the profile columns). Limits are tuned with the `PUBLIC_*` settings in `.env.example`.
- Chat assistant (ADR 0011): set `CHAT_LLM_API_KEY` (and `CHAT_LLM_*` if not Sarvam) on the API project, then turn the clinic's chat on with `PATCH /v1/admin/clinic {"public_chat_enabled": true}` (owner or admin; the clinic must already be public). Without the key the assistant only offers quick replies and the fallback text. Approve the emergency script first: until `scripts_approved`, emergencies get the platform default text.
- Staff "Call now" on callback requests needs, per clinic: `outbound_enabled`, an outbound agent (`bolna_outbound_agent_id`), the caller number (`PATCH /v1/admin/clinic {"bolna_outbound_from_number": "+91..."}`, owner only) and `BOLNA_API_KEY` on the API project. Each call needs explicit owner authorization against the live API (AGENTS.md); it counts against the clinic's daily contact budget and respects quiet hours. A request stuck in `calling` with no execution id timed out at Bolna: check the Bolna dashboard for the call, then resolve it as done or dismissed. `GET /v1/staff/outbound-status` shows what is missing.
- Demo data: `clinic-voice seed-platform` (needs `TOKEN_ENCRYPTION_KEYS` and `PHONE_HASH_KEY`) creates the synthetic Aster Dental Studio (`aster-dental`) with ledger calendars, about 70 appointments, callbacks and four chat conversations (chat turned on), all marked `synthetic` with no consents, so nothing seeded is ever contacted; re-running tops up what an interrupted run left and adds nothing otherwise. It refuses when any non-seed clinic exists, creates no staff users and leaves `outbound_enabled` off. Use it only on a demo database.
