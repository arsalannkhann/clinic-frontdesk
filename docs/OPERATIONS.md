# Development and operations

## Local lifecycle

Follow README setup. `docker compose stop` preserves data; `docker compose down` also preserves the named volume. `docker compose down -v` deletes local data and must only be used intentionally. Migrations run as a separate CLI step before API start, from the repository root. The application never auto-creates tables. The schema lock serializes migration processes, and checksums reject edits to applied files.

The image runs as UID 10001. Build with `docker build -t clinic-voice:dev .`; pass DATABASE_URL through your environment/secret manager. Issue tool credentials with the CLI after migrating; the plaintext token is printed once and must go straight to the gateway's secret store. Inside a Compose network the DB hostname is `db:5432`, not localhost:55432. The Dockerfile does not run migrations on startup. No deployment automation is configured.

Readiness checks schema availability and reports integrations `not_configured`. It does not certify calendar sync or a working phone line. Keep liveness separate so a provider outage does not trigger a restart loop. Outbox entries are consumed only while a worker runs (see below).

## Running the worker

`clinic-voice worker --calendar fake` runs the outbox worker in a loop: it claims up to 10 due jobs, processes them, and polls again after `--interval` seconds (default 2, 0.1-300) when idle, reusing one database connection across polls. `--once` processes one batch and exits; `--worker-id` names the lease owner (default `host:pid`, at most 128 characters; use a distinct id per process). SIGINT/SIGTERM let the current job finish and release the batch's unstarted jobs back to pending (due immediately; `max_attempts` grows by one so the unused claim costs nothing). Database errors close the connection, are logged by type, and back off 1, 2, 4 ... up to 30 seconds before reconnecting. `--calendar fake` uses an in-process FakeCalendar and prints a warning: nothing reaches a real calendar, and events vanish when the process exits. It is refused unless the database name ends in `_test` or `_dev` or `APP_ENV=development` is set (`app_env` defaults to `production`). Without `--calendar` the worker refuses to start. `--calendar google` uses the Google Calendar adapter with each doctor's calendar account (or the clinic's only active account when the doctor has none) and refuses to start unless `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` and a valid `TOKEN_ENCRYPTION_KEYS` are set. Its adapter timeout is 10 seconds. Every real adapter must declare `timeout_seconds` of at most a quarter of the 2-minute lease (`check_ports` refuses to start otherwise; only FakeCalendar is exempt). A create job keeps targeting the calendar it first wrote to after a doctor's booking calendar is remapped; new bookings use the new calendar. Run as many workers as needed; `SKIP LOCKED` keeps claims disjoint and fenced completion makes a reclaimed job safe. A worker killed mid-job leaves its job `processing` until the lease expires; another worker then reclaims it and recovers by reading the deterministic event id, unless the job already used all attempts, in which case it is dead-lettered `lease_expired`. `httpx`/`httpcore` logging is set to WARNING in the worker.

`--bolna fake|live` (optional) adds the Bolna port for call reconciliation. Without it the worker enqueues no reconciliation and any `bolna.reconcile` job dead-letters `bolna_unconfigured`. `--bolna fake` is refused like `--calendar fake` (FakeBolna knows no executions, so reconcile jobs complete without change). `--bolna live` reads `GET /executions/{id}` with `BOLNA_API_KEY` (refused when unset; 10 s timeout); running it against a real account is an owner decision (AGENTS.md) and has not been done. When idle, housekeeping (at most every 10 minutes) enqueues `bolna.reconcile` for at most `BOLNA_RECONCILE_BATCH` (default 50) call sessions without a final provider status whose start and last provider update are older than `BOLNA_RECONCILE_AFTER_MINUTES` (default 30). Each session is polled at most 6 times, the delay doubling after each poll (30 min, 1 h, 2 h ... capped at 24 h). Sessions still unfinished after that keep `provider_final = false` with `reconcile_count = 6`; review them with `SELECT clinic_id, id, provider_status, started_at FROM call_sessions WHERE NOT provider_final AND reconcile_count >= 6`.

## Google Calendar setup (requires owner action; not performed)

None of these steps has been performed for this repository: no Google Cloud project, OAuth client or calendar exists, and no live Google call has been made. An owner who wants to validate against a real test account does the following with a non-production Google account:

1. In Google Cloud console create a project, enable the Google Calendar API, and configure the OAuth consent screen (External/testing is fine; add the test Google account as a test user). Add the scopes `https://www.googleapis.com/auth/calendar.events` and `https://www.googleapis.com/auth/calendar.freebusy`.
2. Create an OAuth client of type "Web application" with the authorized redirect URI `http://localhost:8000/v1/oauth/google/callback` for local runs (Google allows plain http only for loopback) or the deployment's `https://.../v1/oauth/google/callback`. It must match `GOOGLE_REDIRECT_URI` exactly.
3. Generate the token keyring: `clinic-voice generate-key` prints a key; set `TOKEN_ENCRYPTION_KEYS=k1:<key>` (key ids: 1-32 letters, digits, `_` or `-`). Store the client secret and keys in a secret manager or an untracked `.env`, never in Git. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI`.
4. In the test account create a dedicated booking calendar; note its calendar id. As an owner/admin staff user call `POST /v1/admin/calendar/google/start`, open the returned URL in a browser, consent with the test account, and confirm the callback page says the calendar is connected (`GET /v1/admin/calendar/accounts`).
5. Map a synthetic doctor: `PATCH /v1/admin/doctors/{id}` with `booking_calendar_id`, `busy_calendar_ids` and, if the clinic has several accounts, `calendar_account_id`. Run `clinic-voice worker --calendar google --once` after a synthetic reservation and compare the database, the calendar event and `appointment-status`.

Without these settings the calendar endpoints return 503 "Calendar integration not configured". Key rotation: prepend a new key (`TOKEN_ENCRYPTION_KEYS=k2:<new>,k1:<old>`); new ciphertext uses `k2` and old rows still decrypt with `k1`. Do not remove a key while rows reference it (`SELECT key_id, count(*) FROM calendar_accounts WHERE status <> 'revoked' GROUP BY 1`); there is no re-encryption command yet, so reconnecting the account is the way to move it to the new key. A row whose key is missing makes its jobs dead-letter with `provider_permanent`. Disconnect with `DELETE /v1/admin/calendar/google/{id}`; doctors keep the id and their jobs become `calendar_unmapped` until remapped. Cancels of events written by a disconnected account also dead-letter `calendar_unmapped`: remove those events by hand in the calendar. The Google revocation runs as a `calendar.revoke_grant` outbox job in the `--calendar google` worker (a fake worker dead-letters it `no_revoker`; requeue it once a Google worker runs). If it dead-letters after its retries, the stored token is kept: the owner removes the app's access in the Google account (in the Google Account security settings, under third-party apps with account access; the exact menu path is not verified here) and then requeues the job, which treats Google's `invalid_token` answer as revoked and clears the ciphertext. An account in status `error` means Google rejected its refresh token (user removed access, password reset, or the testing-mode token expired); reconnect with `POST /v1/admin/calendar/google/start?replace=true`. Connecting a second account requires `replace=true`, which retires the old account locally (token forgotten, audit `calendar.account_replaced`) but does not revoke it at Google: Google's revocation is grant-wide, so it would also disable the new account if the same Google user reconnected. If a different Google user was connected before, the owner should remove that stale grant in that user's Google account at https://myaccount.google.com/permissions. A rejected callback (missing refresh token or scopes) is also discarded without a Google revoke; remove the grant there if wanted. An explicit DELETE revokes at Google and therefore also disables any other calendar account connected with the same Google user (those turn `error`). Outstanding cancels whose writing account was revoked or replaced use the doctor's current account. Reconnecting after a disconnect cancels that disconnect's pending Google revocation (job done with `revoke_superseded`) and forgets the old token locally, because it may be the same Google user; if it was a different user, remove the old grant at https://myaccount.google.com/permissions. Known limitation: a disconnect also disconnects the same Google user in other clinics, since accounts are not tied to a Google identity yet (a keyed hash of the Google `sub` via the `openid` scope is a follow-up that needs owner approval). Expired OAuth states are pruned by the worker when idle. uvicorn access-log lines have their query strings stripped (the callback query carries the authorization code); do not enable other request logging that records query strings.

## Bolna gateway setup (requires owner action; not performed)

No Bolna account, agent, number or call has been used by this repository. The gateway routes run in the API process and need `TOKEN_ENCRYPTION_KEYS` and `PHONE_HASH_KEY` (`clinic-voice generate-key` for each; the hash key is a bare base64 key, not `kid:key`). Never rotate `PHONE_HASH_KEY` casually: existing `caller_number_hash` values stop matching. To review the agent payload: set `BOLNA_GATEWAY_BASE_URL` (the public https base URL Bolna will reach) or pass `--gateway-url`, then run `clinic-voice bolna compile-agent --clinic <uuid>`; the output has `Bearer <redacted>` where the tool credential goes. Creating the agent at Bolna, inserting a real token, assigning a number and test calls need explicit owner authorization and a provisioning flow (T10); `BOLNA_API_KEY` and `BOLNA_API_BASE` are read only by `clinic-voice worker --bolna live` (execution reads for reconciliation, T8); provisioning (T10) will use them too. Leave the key unset until the owner authorizes live use. Before enabling, re-run the contract checks in docs/SOURCE_REVIEW.md against a test agent: tool request body shape, `execution_id`/`from_number` substitution, multilingual switching and the Sarvam voice id.

## Bolna webhook setup (requires owner action; not performed)

No Bolna delivery has reached this code. To prepare one:

1. `clinic-voice credential issue --clinic <uuid> --label bolna-webhook --scope webhook` prints `token=cvw_...` and `webhook_path=/v1/webhooks/bolna/cvw_...` once. The webhook URL is `<public https base>/v1/webhooks/bolna/<token>`; treat the whole URL as a secret. Set it as the agent's `webhook_url` (dashboard or agent update; the compiler does not set it yet). Bolna documents no signing or API-settable headers, so do not rely on the dashboard's "Add headers" toggle.
2. `clinic-voice bolna set-agent --clinic <uuid> --agent-id <bolna agent uuid>` records the agent id; deliveries naming another agent are then refused (403). `--clear` removes it.
3. Optional: `BOLNA_WEBHOOK_ALLOWED_IPS=13.203.39.153,13.126.9.249,13.202.133.53` (recheck the addresses on Bolna's webhook page first). Behind a reverse proxy set `TRUSTED_PROXY_HOPS` to the number of proxies that append to X-Forwarded-For; otherwise the proxy's own address is checked and every delivery is refused. `WEBHOOK_MAX_BODY_BYTES` (default 65536) caps the body.
4. Configure the proxy/load balancer not to log paths under `/v1/webhooks/` (or redact the last segment); the application's own access log already redacts it.
5. Run a worker so `webhook.process` jobs are applied. Rotation works as for tool credentials (`credential rotate`, update `webhook_url`, watch `last_used_at`, revoke). Inspect deliveries with `SELECT received_seq, execution_id, provider_status, status, outcome FROM webhook_inbox WHERE clinic_id=... ORDER BY received_seq`: `ignored` + `unknown_execution` means the call never reached the tool gateway; `stale` means an out-of-order or post-final status; `agent_mismatch` means the session's agent differs. A dead `webhook.process` job marks its event `failed`; requeue it after fixing the cause and the event is processed again.

## Retention purge (operator-run; not scheduled)

`clinic-voice retention purge --dry-run` prints how many patients, consents, appointment links and call sessions a purge would remove, then rolls back; without `--dry-run` it deletes them in one transaction. Patients whose `retention_until` (latest appointment start + `PATIENT_RETENTION_DAYS`, default 365) has passed are deleted with their consents unless they still hold an active appointment that has not ended; their appointments stay with `patient_id` cleared. Webhook inbox events received more than `CALL_SESSION_RETENTION_DAYS` ago are deleted (`webhook_events`). Call sessions older than `CALL_SESSION_RETENTION_DAYS` (default 90) are deleted with their verification records after `appointments.call_session_id` and `appointment_changes.call_session_id` are cleared. Output is counts only. Nothing runs it automatically; schedule it only after the owner approves a retention policy. Back up first: deletion is permanent.

Reschedules release the original slot before the new booking's calendar sync completes. Watch `needs_review` appointments with a `rescheduled_from` and call those patients; the clinic must approve that spoken wording (ADR 0006) before pilot traffic.

Migration 012 was revised before release (backfill and indexes). Databases that applied the earlier branch-only version of `012_patients.sql` fail the checksum check: recreate them (`docker compose down -v` for local data, or drop the `_test` database's schema). Released databases are unaffected (012 has never been on `main`).

Staff can review appointments at `GET /v1/admin/appointments` and settle `needs_review` ones with `POST /v1/admin/appointments/{id}/resolve` (`requeue` after fixing the cause, or `cancel`). Callers who hit the verification handoff (3 failed booking references in one call) must be helped by staff.

## Dead-letter review

Jobs dead-letter after `max_attempts` (8) failures or on an outcome retrying cannot fix: `external_conflict` (the doctor's busy calendar overlaps the hold), `calendar_unmapped` (doctor has no booking calendar), `event_mismatch` (an event with the deterministic id exists with other times or is cancelled), `appointment_past` (the appointment started before it could be projected), `lease_expired` (workers kept dying on it), `provider_permanent`, `unknown_kind` (a kind with no handler yet), `bolna_unconfigured` (a reconcile job in a worker without `--bolna`), `execution_mismatch` (Bolna returned another execution's id), `bad_payload`. A dead calendar.create moves a still-pending appointment to `needs_review`; the caller is told staff will follow up. Owners and admins list them with `GET /v1/admin/outbox?status=dead`. Resolve the cause first (map the calendar, clear the conflicting external event, or contact the patient), then `POST /v1/admin/outbox/{id}/requeue`: it keeps `attempts`, grants 8 more (`max_attempts = attempts + 8`), and for a calendar.create whose `last_error` is a calendar failure code returns the appointment to `pending_sync`; the worker re-checks everything before writing. Requeue is refused (409) once the appointment has started, and at once for a job that is not dead (including one being dead-lettered at that moment). Do not requeue `external_conflict` without resolving the conflict; it will dead-letter again. Monitor `pending` age and `processing` jobs whose lease keeps expiring.

## Credential rotation

1. `clinic-voice credential rotate <old-id> --grace-minutes 60` prints the replacement token; the old credential now expires within the grace window (rotation never extends an existing expiry).
2. Deploy the new token to the caller: recompile the Bolna agent with it and update the agent (the provisioning flow is planned; today an owner would do this by hand).
3. Confirm `last_used_at` on the old credential stops advancing (`credential list --clinic <uuid>`; resolution is about five minutes), then `clinic-voice credential revoke <old-id>`.

For a suspected leak, revoke first; revocation is effective on the next request. Migration 002 drops nothing; `TOOL_TOKEN`/`CLINIC_ID` environment variables are now ignored and should be deleted from deployed environments.

## Staff bootstrap and recovery

Create a clinic's first owner with `clinic-voice staff create-owner --clinic <uuid> --email <address>`; the password is read from a hidden prompt or a single stdin line, never from arguments. The owner then creates other staff via `POST /v1/staff/users`. To recover a locked-out or forgotten account run `clinic-voice staff set-password --email <address>`: it clears the lockout, revokes every session for that user and writes a `staff.password_reset` audit event. Migration 003 only adds tables.

## Proposed pilot runbook

1. Record the commit/image digest and migration version; back up DB and verify restore procedures.
2. Run CI including real PostgreSQL races and tenant isolation; provision nonproduction credentials.
3. Configure a dedicated test calendar, verified test numbers, provider headers and inbound routing; validate provider schema with real sanitized responses.
4. Enable one synthetic clinic and make authorized test calls. Verify DB appointment, actual calendar event, notification receipt, outbox state, and spoken status agree.
5. Exercise duplicate tools, lost webhook, worker restart, provider timeout after success, and human calendar edits. Validate cancellation stops reminders and failed reschedule preserves original booking.
6. Enable limited pilot traffic only after owner review of the recorded evidence and unresolved risks. Set per-clinic spend/rate caps and a staffed fallback.

## Failure handling to implement

Calendar uncertain (implemented in the worker): keep pending/review state, reconcile using stable event ID; never blindly reinsert or announce success. Messaging failure: preserve appointment, retry delivery independently and alert after bounded attempts. Webhook gap (implemented, T8): reconciliation polls executions of unfinished sessions with backoff. Reminder race: version-check before dialing and reconcile provider cancellation. Database failure: fail closed with a retryable safe response.

Proposed metrics: booking outcome counts, tool latency, pending reservation age, outbox age/retries/dead letters, calendar conflicts, webhook gaps, transfer failures, language task success and provider spend. Use opaque correlation IDs; no patient identifiers as metric labels.

Rollback app versions only if compatible with schema. No automatic down migrations are provided. Restore from backups only under a reviewed recovery plan; keep the reservation ledger and external calendar reconciled.
