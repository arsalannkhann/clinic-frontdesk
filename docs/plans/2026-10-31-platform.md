# Clinic platform: one product for web, chat and voice (plan, 31 October 2026)

## Goal

Merge the AppointmentBooking ("MedDent") demo into voice-ai so that one deployment serves:

- a public clinic website (the landing page of a realistic synthetic clinic) where patients book online, chat with an assistant or call the voice receptionist;
- a staff console with a real calendar, appointments, callback queue, conversations, and clinic settings;
- the existing Bolna voice receptionist, using the same booking ledger;
- staff-initiated outbound callbacks.

Every channel uses one PostgreSQL database (Supabase project `aqnykbbcabpqgcglqfkw`, eu-west-1) and one backend (voice-ai FastAPI). The voice-ai booking invariants stay in force for every channel: GiST exclusion, lock order (`locks.py`), outbox confirmation, encrypted patient data, and audit.

## What we keep from each repo

AppointmentBooking is a demo with roughly 4,300 lines, no auth, no migrations, string dates, and an LLM that invents slots. Its backend is dropped.

Ideas we port, rewritten:

- the operatory-style calendar grid (one column per resource, 15-minute rows, positioned blocks, detail panel);
- the chat shell (bubbles, typing state, proposal card);
- the doctors, services and live-slot pages;
- the domain idea of procedure colours.

Its committed Cloud SQL password (commit `cd2fc42`) must be rotated by the owner.

voice-ai stays the system of record:

- migrations 001–017;
- staff auth, sessions and roles;
- admin API, scheduling and slots;
- patients, consent and booking references;
- the Bolna gateway, webhooks and reconciliation;
- the outbox worker, reminders and provisioning.

The `dashboard/` Vite app remains the operator console for provisioning, outbox and reminders until the new staff console covers those screens.

## Architecture

```
patients ── web (Next.js on Vercel, /) ──┐            ┌── Bolna (voice, Mumbai) ── phone / web call
                 chat widget             │ BFF /api/* │
staff ───── web (/staff, httpOnly cookie)┘            │
                                         ▼            ▼
                         API (FastAPI on Vercel Python, region dub1)
                           /v1/public/*   /v1/chat/*   /v1/staff/* /v1/admin/*
                           /v1/bolna/*    /v1/webhooks/bolna/*  /v1/internal/worker/tick
                                         │
                         Supabase Postgres (transaction pooler :6543)
                           pg_cron + pg_net ── every minute ──► /v1/internal/worker/tick
```

Decisions:

1. **Two Vercel projects from this repository.**
   - `clinic-platform-api` is the repository root, deployed as Python serverless running the FastAPI `app`.
   - `clinic-platform-web` is the `web/` directory, a Next.js App Router app.
   - The browser only talks to the web origin. Next.js route handlers proxy to the API (the BFF pattern), so there is no browser CORS and the staff session lives in an `httpOnly; Secure; SameSite=Lax` cookie.
   - The API keeps CORS off.

2. **Serverless database access.**
   - Serverless instances use the Supabase transaction pooler (port 6543) with psycopg `prepare_threshold=None`.
   - Only transaction-scoped advisory locks are used, and the code already does this.
   - No session state, LISTEN or prepared statements are relied on.
   - Local development and tests keep plain PostgreSQL.

3. **The worker runs as a bounded tick, not a daemon.**
   - `POST /v1/internal/worker/tick` is authenticated by `WORKER_TICK_SECRET`. It claims and runs jobs until a time budget is spent (default 8 s), then runs housekeeping.
   - Supabase `pg_cron` calls it through `pg_net` every minute.
   - The public and chat booking paths also run the booking's own `calendar.create` job inline, within a short budget, so a web booking normally confirms before the response returns.
   - The long-running `clinic-voice worker` CLI still works for local and VM hosting.

4. **The ledger calendar provider.**
   - For clinics without Google Calendar, the platform ledger is the calendar of record. The `ledger` calendar port treats an insert as success with the deterministic event id, cancel as success, and free/busy as empty.
   - Doctors mapped to `ledger:` calendar ids confirm through the normal outbox path. Doctors mapped to Google calendars keep the Google adapter.

5. **Supabase hardening.**
   - Supabase exposes `public` through PostgREST to the `anon` and `authenticated` roles. A migration enables RLS on every table and revokes table, sequence and function privileges from those roles, including default privileges.
   - The migration is guarded so it is a no-op on plain PostgreSQL where the roles do not exist.
   - Only the backend's `postgres` connection touches data. The Supabase anon and service keys are not used by any client.

6. **The chat assistant.**
   - It is server-side and tool-using. The model is OpenAI-compatible and configured by `CHAT_LLM_BASE_URL`, `CHAT_LLM_MODEL` and `CHAT_LLM_API_KEY`. The default is Sarvam `sarvam-105b`, which was verified to emit tool calls on 31 October 2026. The Gemini key in AppointmentBooking is invalid.
   - History is stored on the server, and the client sends only its new message.
   - Tools call the same service functions as the voice gateway:
     - `clinic_info`
     - `list_services`
     - `check_slots`
     - `propose_booking`
     - `booking_status`
     - `request_callback`
   - `propose_booking` never writes an appointment. It stores a short-lived proposal, and the UI shows a confirmation card. Only the patient's click, `POST /v1/chat/sessions/{id}/proposals/{pid}/confirm`, books, with name, phone and consent collected in that card.
   - A failing LLM degrades to guided quick replies.
   - Emergencies get the clinic's approved emergency script. The assistant does not diagnose or advise on medication.

7. **Outbound callbacks.**
   - Patients request a callback from the website, the chat, or the voice agent's handoff. The request goes into `callback_requests`, and staff see a queue.
   - "Call now" in the console places a Bolna outbound call (`POST /call`) with the clinic's configured outbound agent and from-number.
   - The call is refused unless the clinic's `outbound_enabled` is on, a from-number is set, and the staff role is owner or admin. Every attempt is audited.
   - Nothing ever dials automatically. No number is purchased; the owner configures one.

8. **AI disclosure.**
   - The chat says it is the clinic's virtual assistant.
   - The receptionist prompt in the working tree has an uncommitted owner edit that removes the voice disclosure. That edit is left untouched and flagged to the owner: disclosure is recommended and may be legally required.

## Data model changes (new migrations; 001–017 are frozen)

**018_platform.sql**

- `services.description`, `services.public` and `services.colour` (a hex string, for calendar blocks).
- `doctors.public_bio`, `doctors.photo_url` and `doctors.colour`.
- `appointments.channel` (`voice` | `web` | `chat` | `staff`), defaulting to `voice` for existing rows.
- `callback_requests`:

  | Column | Notes |

  | `id`, `clinic_id` | |

  | `name_ciphertext` | |

**019_chat.sql**

- `chat_sessions`: id, clinic_id, created_at, last_active_at, ip_hash, status, turn_count, and patient_id (nullable).
- `chat_messages`: session_id, seq, role (`user` / `assistant` / `tool`), content ciphertext, tool name, and created_at.
- `chat_proposals`: id, session_id, doctor_id, service_id, starts_at, expires_at and consumed_at.
- Content is encrypted with the existing keyring, because chats contain health details.
- Retention follows the existing purge command.

## API contract (backend; the web app builds against it)

All public routes take the clinic by slug, for example `/v1/public/clinics/{slug}/...`. They return no other patients' data.

Error envelope: `{"error": {"code": str, "message": str}}`.

Limits are per IP (hashed with `PHONE_HASH_KEY`) and per phone, and a breach returns `429 rate_limited`.

The BFF forwards the client IP in `X-Forwarded-For`. The API trusts only the configured proxy hop count (`TRUSTED_PROXY_HOPS`).

| Method | Path | Request | Response |
| --- | --- | --- | --- |
| GET | `/v1/public/clinics/{slug}` | – | `{name, tagline, timezone, address, map_url, phone_display, email, hours_note, about, voice_number, chat_enabled}` |
| GET | `/v1/public/clinics/{slug}/services` | – | `[{id, name, description, duration_minutes, colour}]` |
| GET | `/v1/public/clinics/{slug}/doctors` | – | `[{id, name, public_bio, photo_url, colour, service_ids}]` |
| GET | `/v1/public/clinics/{slug}/slots` | `?service_id&doctor_id?&date=YYYY-MM-DD&days=1..7` | `{timezone, slots:[{doctor_id, starts_at, ends_at}]}` |
| POST | `/v1/public/clinics/{slug}/bookings` | `{service_id, doctor_id, starts_at, name, phone (E.164), consent_contact: bool, notes?}` | `202 {reference, status: pending_sync\|confirmed, starts_at, doctor_name, service_name}` |
| POST | `/v1/public/clinics/{slug}/bookings/lookup` | `{reference, phone}` | `{reference, status, starts_at, doctor_name, service_name}` or uniform `404 not_found` |
| POST | `/v1/public/clinics/{slug}/callbacks` | `{name, phone, reason?}` | `201 {id, status}` |
| POST | `/v1/chat/clinics/{slug}/sessions` | – | `201 {session_id, greeting, quick_replies: [str]}` |
| POST | `/v1/chat/sessions/{id}/messages` | `{text ≤ 1000}` | `{messages:[{role, text}], proposal?: {id, doctor_name, service_name, starts_at, expires_at}, quick_replies:[str]}` |
| POST | `/v1/chat/sessions/{id}/proposals/{pid}/confirm` | `{name, phone, consent_contact}` | same as public booking |

Chat session ids are 128-bit random and act as bearer secrets for that conversation only.

Staff routes use the existing `Authorization: Bearer <session>`, roles and audit:

| Method | Path | Request | Response |
| --- | --- | --- | --- |
| GET | `/v1/staff/calendar` | `?from&to` (≤ 31 days) | `{timezone, doctors:[{id, name, colour}], appointments:[{id, doctor_id, service_id, service_name, colour, starts_at, ends_at, status, sync_state, channel, patient_name?, reference?}], exceptions:[...]}` |
| POST | `/v1/staff/bookings` | `{service_id, doctor_id, starts_at, name, phone, notes?}` | staff booking, channel `staff` |
| GET | `/v1/staff/callbacks` | `?status` | `[{id, name, phone_masked, reason, source, status, created_at}]` |
| POST | `/v1/staff/callbacks/{id}/call` | – | `202 {status: calling, execution_id}`, or `409 outbound_disabled` / `409 no_from_number` |
| POST | `/v1/staff/callbacks/{id}/resolve` | `{status: done\|dismissed}` | – |
| GET | `/v1/staff/conversations` | `?channel=chat\|voice` | `[{id, channel, started_at, status, turns, patient_name?, outcome}]` |
| GET | `/v1/staff/conversations/{id}` | – | chat transcript (decrypted for staff), or call session summary |
| GET | `/v1/staff/stats` | – | `{today, week, needs_review, open_callbacks, by_channel:{voice, web, chat, staff}}` (real counts only) |

The existing routes under `/v1/staff/*`, `/v1/admin/*` and `/v1/bolna/*` keep their contracts.

## Web app (`web/`)

- **Stack:** Next.js 14 App Router, TypeScript strict, Tailwind, own small component set (no template look), `lucide-react` icons, and `next/font`.
- **Data and routes:** server components fetch public data. Staff pages use client components with SWR through `/api/staff/*` route handlers.

**Public pages**

- `/`: clinic landing page with a hero, services, doctors, patient-journey and "three ways to book" (online, chat, call), reviews (labelled as sample content), location and hours, FAQ, and footer.
- `/book`: stepper (service, then doctor or "any", then date strip and slot grid, then details and consent, then confirmation with reference).
- `/booking`: lookup by reference and phone.
- `/callback`: request a callback.
- A chat launcher on every public page, with streaming-style typing, quick replies and the proposal card.

**Staff pages**

- `/staff/login`
- `/staff`: today view with real stats and the needs-review queue.
- `/staff/calendar`: day view with doctors as columns and week view; blocks coloured by service with status and sync badges; a current-time line; a detail drawer with cancel and resolve; click an empty slot to create a staff booking.
- `/staff/appointments`
- `/staff/callbacks`: queue with "Call now", disabled with the reason shown when outbound is off.
- `/staff/conversations`: chat and voice transcripts.
- `/staff/settings`: clinic profile, doctors, services, hours and exceptions.

**Design direction**

The look is warm and clinical-editorial, not a default SaaS template:

- an off-white paper background, deep ink text, and one confident accent colour;
- a serif display face paired with a humanist sans;
- generous whitespace, real copy instead of lorem, and photography-free illustration with shapes and type;
- no gradient blobs, no emoji icons, no fake metrics;
- accessible contrast, focus states and reduced-motion support;
- correct layout at 360 px.

## Seed data (synthetic, clearly fictional)

`clinic-voice seed-platform` is idempotent and refuses to run if the target holds non-seed clinics.

- **Clinic:** "Aster Dental Studio", Indiranagar, Bengaluru, slug `aster-dental`, Asia/Kolkata.
  - Five doctors with specialities, colours and weekly hours.
  - Ten services (check-up and cleaning, whitening, fillings, root canal consult, extraction, implant consult, aligner consult, kids' check-up, emergency pain visit, crown fitting) with durations, buffers and colours.
- **Exceptions:** Diwali clinic holiday on 8 November 2026 and one doctor's leave.
- **Appointments:** about 70 appointments over the past 7 and next 14 days, across all channels and statuses.
  - Synthetic Indian names.
  - Phone numbers drawn from the reserved fictional range `+91 90000 0xxxx`.
- **Other rows:** a few callback requests and chat sessions.
- **Staff:** an owner account for the owner's email, with the password set interactively by the owner.
